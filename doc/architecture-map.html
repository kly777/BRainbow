01 · Executive summary

先看五条判断

BRainbow 不是单一知识库，而是一个“12 个工具 + 1 个外壳”的组合式 PKM。架构的强项是组合根与端口；弱项是同一件事的多套实现，以及几个从未接上的孤岛。

四条用户旅程 · 产品真正承诺的东西
结构判断

强项：三处“只写一次”

  • 组合根：app/context.rs 是唯一认识所有模块的地方；模块之间不互相 new。
  • SearchPort：10 个 provider 并行聚合，新增搜索源不需要改聚合层。
  • 单一声明 schema：新库、老库、自检共用 db/schema 一份声明。
  • Actor：admin / 普通用户的归属判据只有一处。

弱项：同一件事的多套做法

  • 标签：tag / file_tag / bookmark_tag 三套表、三套服务、三套 UI。
  • 文本：card / chunk / text_note / reading_article / chat_node / bookmark / file.text_content / conv，八处存储。
  • 检索：模块内 FTS、全局 SearchPort、各域 search 端点、conv 遗留搜索、命令面板，五层入口。
  • AI：前端拼 prompt 的 /ai/chat 与后端编排的 /chat/.../chat 两条路径。

05 · Dependencies

依赖图：契约 vs 实际

契约是 modules → db + shared，app 只做组合。实际有 6 条反向/环状边，以及一条最值得修的分层倒置：file → app。

默认只画跨域与组合边；勾选「显示基础设施边」看 module → shared / ui 的全量引用。

耦合热力图 · 谁 import 谁

最值得修的四条

  • file → app：file/handler.rs:408 直接拿 AuthService 与 optional_actor。模块依赖组合层，无法独立测试。
  • task ↔ time_window：17 条正向 + 2 条反向；反向只用到了 ServiceError 映射，却把两个域的生命周期绑死。
  • user → admin：user/handler.rs:12 拿具体 AdminService，而 AdminServicePort 已经存在。
  • search 注册是手写的：app/context.rs 逐个 register；新模块忘了就静默搜不到。

可以接受的依赖

  • modules → shared / db：契约允许；shared 是工具箱，db 是 schema 声明。
  • app → modules：组合根必须认识所有模块；这是它的职责。
  • chat / bookmark → ai：经 AiChatPort 接缝，方向正确；handler 里拿具体类型是待收口的小问题。
  • 前端 modules → app/context/auth：分层门禁明确允许（auth 是环境）。

06 · Overlap & redundancy

六组“同一件事的多种做法”

冗余不一定是错：有些是历史迁移，有些是不同作用域。真正的问题是它们各自演化、各自测试、各自长 UI。

07 · What to cut

不需要的实现：候选清单

按证据强度排序，不是按个人喜好。每一行都能指到代码出处；“动作”是建议，不是命令。

对象体量证据判断建议动作置信 / 风险

不要误删

  • office_oxide：直接引用为 0，但它是 pdf_oxide 的版本钉；删了 PDF 抽取编译不过。
  • schema 的三份 DDL 文本：看起来像重复，实际是“新库 / 老库 / 自检”共用的同一份声明。
  • file 的预览懒 chunk：首屏看不到，不等于没人用；PDF/3D/Office 都是按需加载。
  • xtask 7.3k 行：不是运行时，但部署/回滚/备份都靠它；别按“业务代码规模”判它。
  • 55k 行测试：贵，但它是这个项目敢做 schema 重构与多用户隔离的底气。

价值 × 复杂度

横轴是生产行数（对数），纵轴是主观价值（1–5）。右下角是“花了很多代码、但用户价值有限”的区域；右上角是必须保留的核心重镇。

08 · Target architecture

如果重画：更少的重复，不是更少的模块

目标不是把 17 个域压成 5 个，而是让“标签、文本、搜索、AI、设置、查看器”各只有一条主路径。模块可以多，重复必须少。

09 · Method & appendix

数字怎么来的，以及它们不能证明什么

静态分析能证明“有没有这行 import”，不能证明“运行时有没有走到”。LOC 是复杂度代理，不是价值度量。

口径

  • 快照：commit 3679c3dd，工作树干净；日期 2026-10-17。
  • 生产行：去掉每个文件第一个 #[cfg(test)] 之后的行，以及 tests.rs；前端去掉 *.test.ts(x)。
  • 依赖边：正则扫描 Rust crate::modules::* / crate::app::*，前端 @modules/*、@app/*、相对 import；计数是引用次数。
  • 端点：按路由注册表统计方法级端点，共 159；表：db/schema/tables.rs 的 34 张基表。

局限

  • 看不到动态分发与 registry：SearchPort 的 10 条边不是 import，是运行时注册。
  • 看不到“功能是否真的被用户使用”；本地库近乎空库，不能拿行数当使用率。
  • “价值 1–5”是分析判断，不是埋点数据；它只用来把讨论从“代码多不多”拉到“值不值”。
  • 删除建议没有考虑外部 API 消费者；sign 若被脚本调用，应先看访问日志。
  • 文档漂移（已部分处理）：doc/ 此前被 .gitignore 忽略，doc/README.md / guides/* 曾不在工作区；2026-10-22 已汇集入库并完成现行文档对齐（本图谱自身仍是 2026-10-17 快照）。仍存内容漂移：db_viewer 的 feature-gate 描述与 Cargo.toml 不一致。
