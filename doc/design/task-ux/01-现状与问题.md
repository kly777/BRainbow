## 1. 录入：现状比预期好

一个必须先纠正的常见误解：**"创建任务要填很多字段"在当前代码里不成立。**

后端 `CreateTaskRequest`（`src/modules/task/dto.rs:8-23`）只有一个必填字段：

```rust
pub struct CreateTaskRequest {
    pub title: String,                    // 唯一必填
    #[serde(default)] pub description: Option<String>,
    #[serde(default)] pub parent_task_id: Option<i32>,
    #[serde(default)] pub effort_estimate_minutes: Option<i32>,
}
```

另有 `QuickCreateTaskRequest`（`dto.rs:27-30`），**只有 `title` 一个字段**。

前端有三个录入入口，全部只要求标题：

| 入口 | 位置 | 行为 |
|---|---|---|
| 工具条快速添加 | `web/src/modules/task/components/TaskToolbar.tsx:44-61` | 单行 `<input>`，placeholder `+ 快速添加…`，回车提交，焦点留在输入框 |
| 内联添加子任务 | `components/TaskItem.tsx:102-139` | 点行末 `+` 展开输入框，回车提交 |
| 全局快速记录 | `web/src/modules/quick-capture/hooks/useQuickCapture.ts:116-125` | `Shift+Tab` 唤起浮窗，`#` 前缀 → 任务 |

而且**不存在"新建任务"表单**。`EditTaskModal.tsx:75` 早退 `if (!props.task) return`，它只能编辑已存在的任务。

> **结论 1**：录入的"必填项太多"这个问题**不存在**。真正的问题在别处，见 §4。

## 2. 编辑：三个能力割裂的入口

同一个任务的属性散在三处不同的界面，且能力不一致：

| 入口 | 能改什么 | 问题 |
|---|---|---|
| `EditTaskModal`（列表页点铅笔） | 标题/描述/状态/工时/父任务 + 时间段 + 依赖，三个 tab | 打开即并发两个请求拉时间窗（`EditTaskModal.tsx:44-58`）；保存是**全量提交**，5 个字段无论改没改都发出去（`:76-82`）；保存按钮**无 disabled**（`:100-102`），空标题也能提交（后端 `validate_title` 会拒，但用户看不到原因） |
| `TaskKanban` 内的编辑框 | **只有标题** | `TaskKanban.tsx:203-233` 硬编码标题为「编辑任务标题」，无法改描述/状态/工时/父任务 |
| `TimeWindowsTab` | 时间窗 | 只能手工新建，`Select` 只有 `feasible 🟢` / `planned 🔵` 两项（没有 `actual`），另有 5 个硬编码预设（3 个"今天"、2 个"明天"，`TimeWindowsTab.tsx:19-23`） |

`status` 字段在 `UpdateTaskRequest`（`dto.rs:34-54`）里是**可被 PATCH 任意改写**的，绕过全部流转规则；同时又有 4 个独立端点 `/complete` `/activate` `/archive` `/move-to-backlog`。也就是说"改状态"有两条口径不同的路。

## 3. 排程：后端零能力

`src/modules/time_window/` 全模块只有 3 个写方法（`create` / `update` / `delete`）和 4 个读方法（`by_id` / `list_by_task` / `get_task_time_stats` / `check_time_conflict`）。

**没有任何排程、建议、评分、找空闲的能力。** 具体地：

- 冲突检测存在**两套语义不同的实现**：
  - 写路径 C002（`src/modules/task/service.rs:232-258`）：**按 type 分桶**，桶内 O(n²) 两两比较 `sa < eb && sb < ea`，循环窗口先展开（单窗上限 500 段）。跨类型不比较。
  - 读路径 `check_time_conflict`（`time_window/repository.rs:429-461`）：**不分 type**，任意两段重叠即冲突；**不展开循环**。
  - DB 层无任何排他约束来兜底。
- 约束 C001（`task/service.rs:260-268`）：每个 `planned` 段必须被**某个** `feasible` 段**完全包含**。注意是"某个"，多个 feasible 段拼接出的连续区间不算覆盖。
- 循环展开 `TimeWindow::expand_between`（`time_window/model.rs:163-240`）是**已实现但基本无人使用**的能力：月度的注释说"该月跳过"，而测试 `expand_monthly_clamps_to_month_end`（`model.rs:486-506`）证明实际是钳制到 2/28——**注释与行为不一致**。
- `update` 路径上若只改 `window_type` 或 `user_id`，**完全跳过 C001/C002 校验**（`time_window/service.rs:87`）；`recurrence_*` 在 update 路径不接受修改（`:109-112`）。

**已有一个可直接借鉴的先例**：`src/modules/mem/selection.rs:53-99` 是全仓唯一成型的"打分 + 排序/推荐"实现（FSRS 召回紧迫度 × 难度 × 遗忘次数 × 逾期天数，用 Efraimidis–Spirakis 指数竞速做不放回加权采样）。它与 task 模块**无任何代码共享**，但证明了这个项目接受加权打分这条路。

## 4. 五个具体缺口

### 缺口 A：无法表达"什么时候之前要做完"

`task` 表全部 10 列（列与约束逐字照抄，源码里的行内注释与空白已省略）：

```sql
CREATE TABLE IF NOT EXISTS task (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    description TEXT,
    parent_task_id INTEGER,
    status TEXT DEFAULT 'backlog',
    completed_at TIMESTAMP,
    effort_estimate_minutes INTEGER,
    user_id INTEGER,
    created_at TIMESTAMP DEFAULT (strftime('%Y-%m-%dT%H:%M:%S+00:00','now')),
    updated_at TIMESTAMP DEFAULT (strftime('%Y-%m-%dT%H:%M:%S+00:00','now')),
    FOREIGN KEY (parent_task_id) REFERENCES task(id),
    FOREIGN KEY (user_id) REFERENCES user(id),
    CHECK (effort_estimate_minutes IS NULL OR effort_estimate_minutes >= 0)
)
```

**没有 `due_at`，没有 `deadline`，没有 `start_at`，没有 `priority`，没有 `tags`。**

关于"分层"的澄清——结构关系确实有多层，但**没有一层与时间有关**：

| 表 | 语义 | 状态 |
|---|---|---|
| `task.parent_task_id` | 树形父子 | 在用，但前端只渲染**一层**子任务（`TaskList.tsx:51` → `TaskItem.tsx:141-156`，子任务 `children` 传 `[]`） |
| `task_dependency` | DAG 依赖 | 在用；**无环检测**（`task/service.rs:138-155` 只拦自环），所以 A→B→A 能写进去，DAG 接口会输出环 |
| `task_decomposition` | 分解关系 | **死表**，全仓无任何代码读写（grep 仅命中 `tables.rs:136-138` 的 DDL 声明） |
| `task_time_allocation` | 任务×时窗分摊时长 | **死表**，同样无任何代码读写 |

> 全库唯一真实的 due 类字段是 `mem.due_at`（`tables.rs:358`），配套 `GET /api/mem/due` 与上面那套加权打分。它属于间隔重复记忆模块，与 task 无关——但**它是这套设计最直接的内部先例**。

### 缺口 B：排序口径是"创建时间倒序"

唯一口径，后端 SQL 决定：所有列表查询都是 `ORDER BY created_at DESC`（`task/repository/crud.rs:34`、`:67`）。

前端不重排：`groupByStatus` / `buildChildrenMap`（`lib/task-group.ts`）是稳定的 push 顺序，继承输入顺序。搜索结果又是另一个口径 `ORDER BY (title LIKE ...) DESC, id DESC`（`repository/query.rs:196`）。

结果：**任务按"我什么时候想起它"排序，而不是按"我什么时候该做它"**。这正是核心痛点。

（注意 `repository/query.rs:221` 那个 `ORDER BY rank` 是 FTS5 的 bm25 相关性排序，不是优先级。）

### 缺口 C：日历上只有手工排过的任务

数据源 `GET /api/tasks/calendar`（`task/repository/query.rs:268-381`）是：

```sql
-- INNER JOIN：没有 time_window 的任务根本不出现
```

渲染方式（`components/TaskCalendar.tsx:43-60`）是**每个日期格内纵向堆叠文本行**，每行 = 开始时间 + 标题。缺失的能力：

- 只有**月视图**，没有周/日时间轴，没有小时刻度
- 跨天事件**只落在起始那天**（`useTaskCalendar.ts:56-68` 只按 `ev.start` 的年月日建 Map）
- 点事件**无任何反应**，不能进详情
- 颜色只按 `window_type` 三色，事件自带的 `status` 字段**完全未被使用**
- 不展开循环窗口、不处理重叠布局
- 没有"回到今天"按钮（`changeMonth` 只是 `±1`，`useTaskCalendar.ts:34-38`）
- 补位格的 key 用**未补零的月份**（`` `${y}-${m}-${d}` ``），跨年时与补零格式不一致
- **周起始日写死周日**，对中文用户是错的：表头是硬编码字面量（`TaskCalendar.tsx:88-94` 全写「周日 周一 … 周六」、`:95-101` 简写「日 一 … 六」），网格偏移用 `new Date(y, m, 1).getDay()`（`useTaskCalendar.ts:44-47`，0 = 周日）。CLDR 的 `firstDay` 在 CN 是**周一**（[07](07-调研附录.md) §3.3）

### 缺口 D：没有筛选与排序控件

`TaskToolbar.tsx` 只有三个控件：视图切换（列表/看板）、搜索框、快速添加。**没有任何筛选或排序控件**——不按状态、不按父任务、不按工时，也没有任何排序选项。

### 缺口 E：筛选器形同虚设

`groupByStatus`（`lib/task-group.ts:31-45`）把 `status` 为空串/undefined 的归入 `backlog`，**但未知状态直接丢弃**（`if (status in grouped)`，`:42`）——不进任何分组，在界面上直接消失。

同一个逻辑在 `TaskKanban.tsx:131-143` 被**重写了一份**（只含 3 个状态、显式 `continue` 掉 archived），没有复用 `lib/task-group.ts`。分组逻辑有两处实现。

## 5. 缺口的依赖关系

五个缺口不是并列的，有严格的依赖顺序：

```
缺口 A（无 due/priority 字段）
   └─▶ 缺口 B（排序口径错）    ← 没有 A 就无法算分
   └─▶ 缺口 C（日历表达力）    ← 没有 A，日历上画的仍是"手工时段"而非"承诺"

缺口 D（无筛选排序控件）  ← 独立，但 A 落地后立刻成为瓶颈
缺口 E（筛选器丢数据）    ← 独立 bug，零成本可修
```

这决定了实现顺序：[08-实现路线](08-实现路线.md) 把 A 放在第一阶段。
