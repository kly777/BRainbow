# 02 · 设计原则

> 状态：现行（已实现） · 代码基准：`main@48996cd7`（2026-10-22） · 最后核对：2026-10-22
>
> 十二条判据。每条由「原则 → 来源 → 在本项目怎么落地」三段组成。
> 来源标注：**[官方]** 厂商官方文档 / **[权威]** 第三方权威研究 / **[源码]** 直接读过的实现 / **[本项目]** 现有代码事实 / **[推断]** 我的推理，非引用。

## 录入侧

### P1 · 录入的必填项只能是"这句话本身"

> **原则**：创建一条任务时，唯一必须回答的问题是"我要做什么"。其余一切属性都是可后加的。
>
> **来源**：GTD 的 capture 阶段——收件箱"不需要成型，只需要让你回看时能想起当时的意图"（**[官方]** OmniFocus GTD 白皮书）。NN/g：每个表单项都在消耗用户的"解释—回忆—格式化"三重成本，能删就删（**[权威]** Wang, *4 Principles to Reduce Cognitive Load in Forms*, 2025-07-18）。
>
> **落地**：`CreateTaskRequest` 保持 `title` 唯一必填。新增的 `due_at` / `priority` / `tags` 全部是 `Option`。录入路径上**不允许**出现任何"必填"标记。
>
> **注意当前已满足**（[01](01-现状与问题.md) §1），本条的作用是**守住**——后续加字段时最容易犯的错就是顺手把它设成必填。

### P2 · 连续录入必须能连续进行

> **原则**：回车即创建，**焦点留在输入框**，输入框清空。中间不弹窗、不跳转、不要求二次确认。
>
> **来源**：Todoist / TickTick 官方帮助都是"回车创建"；TickTick 更进一步——`Shift+Enter` 快速加描述，`Cmd+Enter` 才提交。Cultured Code 的口径是"录入越快，你能越快回到手上的工作"（**[官方]**）。
>
> **落地**：任务页的录入框与全局 `Shift+Tab` 浮窗（`quick-capture/hooks/useQuickCapture.ts`）**共用同一个提交函数**，行为完全一致。创建成功只弹 toast，**不移动焦点**。

### P3 · 高级属性走渐进披露，且最多两层

> **原则**：初始面板只显示最重要的少数选项，更大的选项集**按需展开**。披露层级不超过两层。
>
> **来源**：Nielsen《Progressive Disclosure》（2006-12-03）给出三条可直接引用的判据（**[权威]**）：
> - "初始界面上出现的东西，本身就在告诉用户它重要"
> - **"超过两层的披露设计通常可用性很差"**
> - 每一层都要有明确的 information scent（让人知道点进去会看到什么）
>
> 产品级实现参考 Todoist 的 Customize Quick Add：描述默认隐藏，按 `+` 或 `↓` 展开，action 可显示/隐藏/拖拽排序（**[官方]**）。
>
> **落地**：第二层由一个明确的 `+` 按钮唤出，唤出后是**可选**的行内补充（优先级下拉、日期选择、标签多选、工时），全部可留空。第三层不存在——更多属性去任务详情页。
>
> **反面教训**：OmniFocus 的 Return / Shift+Return 在 Modern / Classic 两种大纲模式下行为还不一样（一次 vs 两次，**[官方]**）——这说明披露层一旦变深就会失控。两层是上限，不是起点。

### P4 · 语法符号是有限资源，选定即锁定

> **原则**：符号越少越好；每个符号必须有明确定义；被废弃的符号要有明确退场时间表。
>
> **来源**：Todoist 官方把 `@` 标注为 **"planned to be retired by the end of 2026"**（**[官方]**）——一个符号的迁移成本是真实的。语法符号数量与误报率正相关：Todoist 不得不提供全局关闭开关 + 逐词撤销；RTM 上线 Smart Add 时**主动删掉了"新建后自动选中"**，因为行内语法变强之后行内二次编辑就成了冗余（**[官方/官方博客]**）。
>
> **落地**：见 [03](03-录入模型.md) §2 的完整语法表——**只有 4 个符号**（`#` 标签、`@` 提及、`!` 优先级、`~` 时长），日期不设符号，**走第二层的选择器控件**。

### P5 · 标题行绝不解析；NLP 只能关在专用控件里

> **原则**：**标题行不做自然语言解析**；但"完全不做 NLP"是错的——**NLP 可以做，只要它被关在一个专用控件的输入框里，用户必须主动打开它**。
>
> **来源（支持不做标题行解析）**：Todoist 官方自己举例——"Create **monthly** report" 里的 monthly 被当成了日期，退路是"点击那个词把它变回纯文本"，另加一个全局开关（**[官方]**）。同一份文档也承认不支持捷克语和土耳其语日期——**自然语言解析的覆盖率天花板本身就是产品级风险**。
>
> **来源（推翻"完全不做 NLP"）**：Things 3 **已经支持中文与日文**的自然语言日期输入并默认开启（[官方文档](https://culturedcode.com/things/support/articles/9780167/)，支持 English/German/French/Italian/Spanish/Russian/**Chinese**/Japanese）。一个以"无功能冗余"著称的厂商在 macOS 上这么做，说明中文解析不是不可做。详见 [07](07-调研附录.md) §2。
>
> **关键在于 Things 用什么办法规避了误报**——这是本条真正的收获：
>
> | Things 的做法 | 后果 |
> |---|---|
> | NLP **只在 `⌘S` 打开的 When / Deadline 弹窗里生效** | 标题行永远不解析，所以"Create monthly report"这类误报**结构上不可能发生** |
> | **必须按回车才保存** | 解析结果始终可见、可改、可放弃 |
> | 解析的是**用户刚敲进去的文本**，不是历史数据 | 没有"回看时才发现当初解析错了" |
>
> → **本设计的取舍**：
> 1. **标题行只认显式符号**（`!p1` / `#tag` / `@` / `~60m`）。`!p1` 要么被识别要么不被识别，不存在"我以为它被识别了"。而中文日期的坑是结构性的、不是一个配置项能解决的——读 chrono-node 的 `zh/hans` 源码（**[源码]**）能看到：凌晨 1 点前说"明天"落在**今天**；`前`/`后`/`大前`/`大后` 相对"明天"而非今天（`前`=-2 天）；"下周一"走严格 ±7 周偏移而"周一"取绝对值最小的 diff，**两条路径直觉相反**；"三点"要先定 12 还是 24 小时制；CJK 没有词边界，`patternLeftBoundary()` 只能返回 `()`。这些每一条都要在界面上给用户解释一遍——解释成本高于省下的几次点击。
> 2. **第 2 层的日期控件内允许 NLP**，且**照 Things 的规则做**（必须主动打开、有预览、回车才生效、随时可清空）。这样用户在"我现在就想写'下周一'"的时候有出路，而不用拿整个标题行去赌。
> 3. **解析器设计成可插拔**（[03](03-录入模型.md) §5），标题行与日期控件各挂一条，互不影响。

### P6 · 收件箱要能接住"想做的事"

> **原则**：默认落点不是"待办列表"，是一个可以什么都往里扔的收件箱。
>
> **来源**：Cultured Code 官方指南——"**如果你只录入该做的事，回看待办就会变成一件苦差**"；"**立刻把它们从脑子里卸下来**才是关键"（**[官方]**）。GTD 的底层命题是"脑中的事与这些事被做完之间存在反比关系"（**[官方]** 转引 Allen 2001 原书 p.13–22）。
>
> **落地**：新建任务默认 `status = 'backlog'`，**不要求**填 due/标签/优先级。列表默认视图是"收件箱 + 今天 + 即将到期"，而不是"全部任务按某种顺序"。

### P7 · 录入通道要覆盖"想到就记"的各个场景

> **原则**：录入不应该是一个需要你"走到某个页面"的动作。
>
> **来源**：OmniFocus 3 把 capture 当一等公民做：全局热键（`Control-Option-Space`，应用在跑就能从任何 app 唤起）、Services "Send to Inbox"、Mail Drop（邮件主题→标题、正文→note、附件→附件）、Share 扩展、按换行批量粘贴（**[官方]**）。
>
> **本项目已有**：`Shift+Tab` 全局浮窗（`useQuickCapture.ts`）+ 任务页内联框 + 内联子任务。**本期要做的只是让它们共享同一套语法与提交逻辑**（[03](03-录入模型.md)），不新增通道。

## 排序与排程侧

### P8 · 排序是系统的事，但必须可解释

> **原则**：系统算出"先做哪件"，且**每一条建议都要能说出理由**。
>
> **来源**：GTD 的答案是把决策**移出** capture，而不是让决策更快——澄清是一个有独立仪式的后续活动（每日处理收件箱 / 每周回顾，**[官方]**）。这正说明"决定先做哪件"是一个每天重复消耗的独立活动，值得系统承担。
>
> **本项目先例**：`src/modules/mem/selection.rs:53-99` 的 `review_candidate_weight` 已经是加权乘积 + 指数竞速的不放回加权采样，且 `weighted_policy_exposes_hard_cards_more_than_due_order`（`selection.rs:221`）这样的测试钉住了"加权策略确实比纯 due 排序更早暴露难卡"。新算法沿用同一套形状。
>
> **落地**：打分公式的每一项都对应一个**可读的中文理由**（[05](05-排序与推荐.md) §2）。排序结果里每条任务带 `reason` 字段，界面上直接显示。**不允许**出现无法解释的分数。

### P9 · 系统给建议，人决定落位

> **原则**：自动排程**不写**用户的日历。建议以独立的、明确标注的图层呈现，采纳是一次点击，不采纳零成本。
>
> **来源**：反面证据充分——自动排程的经典失败模式是**过载日**（overbooking）与"算法给出的方案不被用户接受"，以及"日历填满反而降低执行力"。GTD 的原则是**日历只放有硬时间点的事**（会议、预约），任务本身不进日历（**[官方]**）；Cal Newport《Deep Work》的 time blocking 明确反对把任务塞进日历（**[推断]** 该书立场，非产品文档）。
>
> **本轮决策**（[README](README.md)）：只排序 + 给建议，人来落位。系统**不自动创建 `planned` 窗口**。
>
> **落地**：`GET /api/tasks/suggestions` 是**纯读**端点，返回建议时段但**不落库**。采纳 = 前端显式调 `POST /api/tasks/{id}/blocks` 建 `kind="planned"` 的 `task_block`。

### P10 · 建议必须在约束内生成，且约束要可被用户改

> **原则**：建议不是随便挑个空档。要考虑已有安排、截止时间、工作时段偏好——而这些偏好必须是用户能改的设置。
>
> **来源**：Google Calendar 的 "Find time" 本质是**约束求解**而非贪心（对多人空闲求交集），**自动路径建议同理**（**[推断]** 基于该特性的公开行为描述）。已知失败模式正说明约束不全会导致方案不可用。
>
> **落地**：建议算法必须吃三样输入——① 已有 `planned`/`actual` 窗口（不得侵占）② 任务的 `due_at`（建议必须在 due 之前完成）③ 用户的工作时段偏好设置（新增，默认 09:00–12:00 + 14:00–18:00）。三者缺一不可。

### P11 · 数据模型要能表达"这是一个已经兑现的承诺"

> **原则**："我打算周二下午做"与"我周二下午做了"是**两件不同的事**，必须能区分，且互不覆盖。
>
> **来源**：项目现有的 `time_window.type` 三值（`feasible` 可行 / `planned` 计划 / `actual` 实际）已经区分了这三态，但 `TaskDetailResponse`（`dto.rs:58-76`）里**只有字段注释**是它们的唯一文字定义，且 `actual` **不参与** `planned` 的落地校验（[01](01-现状与问题.md) §3）。
>
> **落地**：`actual` 窗口由用户"记录已做"产生，**永不自动创建**。建议算法只读 `planned` 与 `actual`（二者都是硬占用），只写建议不写 `planned`。

### P12 · 每一层的视觉都要服从项目既有的令牌

> **原则**：本目录不发明任何新的视觉语言。录入框、建议条、日历事件块全部走项目现有的 CSS 自定义属性。
>
> **来源**：`web/src/shared/styles/tokens.css`（`--t-*` 颜色/字体/阴影，随主题）+ `web/src/app/global.css`（`--radius-*` / `--space-*` / `--text-*` / `--z-*` 布局常量，不随主题）。两者文件头都写着 `design-system: design.md`，但**该文件在仓库里不存在**——所以令牌的**唯一权威是这两个 .css 文件本身**，改设计先看它们。
>
> **实际可用的令牌**（核实于 2026-10-02，与本设计直接相关的部分）：
>
> | 类别 | 实际令牌 | 备注 |
> |---|---|---|
> | 主题 | `paper`（默认，暖纸）/ `midnight` / `ocean`，共 3 个 + `:root` 兜底 | 由 `theme.ts` 的 `initTheme`/`applyTheme` 切换 |
> | 信号色 | `--t-color-accent` = `oklch(50% 0.08 165deg)` 目录绿；`-strong` / `-soft` / `-ring` | **`--m-task` 就是 `--t-color-accent` 的别名**，任务模块的识别色即信号色 |
> | 语义色 | `--t-color-danger`（`oklch(55% 0.16 25deg)` 偏红）/ `-warning` / `-success`，各有 `-subtle` 浅底版 | **别拿它们编码"重要性"或"逾期"**——见下 |
> | 圆角 | `--radius-2xs` .125rem → `-2xl` 1.5rem → `-full` 999px，**共 7 档** | 不是零圆角世界 |
> | 阴影 | `--shadow-sm` / `-md` / `-lg` / `-lv3`，**每主题一套**（暗色主题的 alpha 更高） | 浮层可以用 |
> | 字体 | `--t-font-display`（**Fraunces 衬线**）/ `-body`（system-ui + 三平台中文面）/ `-mono`（JetBrains Mono） | **没有 `--t-font-numeric`**；数字要等宽得自己在 CSS 里写 `font-variant-numeric: tabular-nums` |
> | 动效 | `--t-transition-fast` 120ms / `-slow` 300ms，`cubic-bezier(0.2,0,0,1)` | |
> | 焦点环 | `--t-ring-accent` = `0 0 0 3px var(--t-color-accent-ring)` | **没有 `--ring-float`**，别引它 |
>
> **两条从"实际令牌"直接推出的硬约束**：
>
> 1. **颜色不能是唯一的信息通道**（WCAG 1.4.1，失败准则 F81）。这不只是审美——项目**确实有** `--t-color-danger`，拿它标逾期、拿 `--t-color-accent` 的深浅标优先级，都是最顺手的写法，也都是不合规的。所以 [06](06-日历视图.md) §5 的三通道里，**边框样式与角标必须是形状/文字**，底色只是冗余的第三条线索。
> 2. **语义色的浅底版（`-subtle`）是本项目表达"弱化"的手法**，不是透明度。所以建议块（[06](06-日历视图.md) §5.3）的淡背景用 `--t-color-accent-soft` / 混色，而不是 `opacity`——后者会让文字一起变淡，在 forced-colors 下直接丢失。

## 冲突裁决

原则打架时按编号取小者，并记录取舍：

| 冲突 | 裁决 | 理由 |
|---|---|---|
| P5（不解析）vs P8（系统代劳） | **P5 胜**：解析不做，但打分要做 | 解析的收益是省几次点击，代价是用户对"系统是否听懂我"的持续怀疑。打分的收益是每天省一次真实决策，代价只是"理由看得懂就行" |
| P9（不自动落位）vs P10（约束求解） | **不冲突** | P10 约束的是建议的**质量**，P9 约束的是建议的**副作用**。约束越准越该让人点采纳，越不该让人放弃 |
| P6（收件箱什么都收）vs P8（排序要有用） | **P8 胜**，但要靠 P6 兜底 | 无 due 无优先级的任务占多数时打分会失效。缓解：给无属性任务一个稳定的次级排序键（见 [05](05-排序与推荐.md) §2.2 末"无信息时的次级排序"），而不是让它随机化 |
| P3（两层披露）vs P4（符号越少越好） | **互补** | 第一层用符号（P4），第二层用控件（P3）。两者都不越界 |

## 明确不做的事

写在这里是为了防止实现阶段"顺手加一点"：

| 不做 | 理由 |
|---|---|
| 自然语言日期/时间解析 | P5，且中文坑是结构性的 |
| AI 自动分类收件箱 | TickTick 已把它写进官方帮助，但**没有任何公开准确率数据**，且与 GTD"capture 阶段不做任何决策"的前提哲学冲突（**[推断]**）。要做也应先做确定性规则 |
| 语音录入 | OmniFocus / Things / TickTick 都有。属于 capture 通道扩展（P7），与本轮目标无关 |
| 精力档位字段 | [README](README.md) 决策表已排除。`effort_estimate_minutes` 已够用 |
| 全自动排程（写库） | P9 |
| 跨用户/共享任务 | 授权模型是"admin 全管、普通用户只管自己创建的"，共享任务需要另一套归属讨论 |
