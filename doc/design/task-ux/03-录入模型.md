# 03 · 录入模型

> 状态：现行（已实现） · 代码基准：`main@48996cd7`（2026-10-22） · 最后核对：2026-10-22
>
> 目标：**让"记下一件事"的成本接近于零。**
> 必填项只有标题一句话，其余属性全部可后加（P1）。

## 1. 三层结构

```
┌─ 第 1 层：常驻单行 ────────────────────────────────┐
│  写周报 !p1 @bob #工作 ~60m                          │
│  ▲ 标题    ▲优先 ▲提及 ▲标签    ▲时长                │
│                                    （无日期）  [+]   │
└─────────────────────────────────────────────────────┘
                        │ 点击 [+] / 聚焦后按 ↓
                        ▼
┌─ 第 2 层：唤出的补充控件（六个，全部可选） ──────────┐
│  截止时间 [2026-10-09 15:00 📅]  开始时间 [      📅]   │
│  优先级 [p1 ▾]  预计 [60 分钟]                      │
│  标签 [#工作 ×][#急 +]   父任务 [写周报 ▾]            │
└─────────────────────────────────────────────────────┘
                        │
                        ▼
┌─ 第 3 层：任务详情页（按需，不在录入路径上） ───────┐
│  描述 / 父子任务 / 依赖 DAG / 时间窗 / 实际执行记录    │
└─────────────────────────────────────────────────────┘
```

**披露层级 = 2**（P3，Nielsen 判据：超过两层可用性就很差）。第三层不参与录入，只在"改已有任务"时出现。六个控件的完整定义见 §3。

**注意第 1 层里没有日期。** 优先级要带 `!`、日期**根本没有符号**（§2.1）——日期走第 2 层的文本控件，这是 MD3 与 Things 都验证过的路子（打字是主路径、日历图标只是入口）。

第 1 层与第 2 层是**同一个输入组件的两个区域**，不是两个界面——第 2 层唤出时焦点仍在标题输入框，展开动画 ≤140ms（`--t-transition-fast`）。

## 2. 第 1 层：显式符号语法

### 2.1 符号表（全部四个）

| 符号 | 含义 | 语法 | 落库字段 |
|---|---|---|---|
| `!` | 优先级 | `!p1` `!p2` `!p3` `!p4`（大小写不敏感）；也接受省略 `p` 的 `!1`…`!4` | `task.priority` |
| `#` | 标签 | `#工作` `#家` `#urgent` | `task_tag` 关联表 |
| `@` | 提及 | `@bob` `@alice` | **本期不入库**，见 §2.4 |
| `~` | 时长 | `~60m` `~1.5h` `~2h` `~90`（裸数字按分钟） | `task.effort_estimate_minutes` |

**日期没有符号。** 这是刻意的：标题行只认上表四个显式符号，而"周内第几天"用符号表达需要一个 mini 语言（`@mon` 还是 `!fri`？），成本高于收益。日期走第 2 层的控件（[02](02-设计原则.md) P5）。

#### 第 2 层日期控件的契约（照 MD3 官方规范）

第 2 层的日期控件是**文本输入 + 日历图标**的组合，两条独立规则决定它怎么工作：

1. **打字是主路径，日历是可选的快捷方式。** MD3 把「Enter dates manually by inputting text, without using the picker」列为第一条用例，并说日历图标"makes interaction with the date picker **optional** and **reduces the amount of key presses** required"（[官方](https://m3.material.io/components/date-pickers/accessibility)）。所以日历图标**只是入口，不是必经之路**。
2. **日期输入框内允许自然语言**（Things 与 MD3 都这么做，见 [02](02-设计原则.md) P5），但必须满足：

| 规则 | 出处 | 落地 |
|---|---|---|
| **失焦或回车时才格式化，输入过程中不格式化** | MD3："Automatically format the date after the user hits 'Enter' or navigates out of the text field. **Don't automatically format the date ... while the user is typing** (also known as input masks) ... because it **changes what they typed**." | **禁止输入掩码**（`2026/10/0` → `2026/10/03` 这类边打边补零要禁）。读屏用户听到的与看到的不一致是这条的真实理由 |
| **接受多种分隔符与不补零** | MD3："accept a range of formats including **dashes, spaces, slashes, dots**, and **0 to the left of a single digit** month/day" | 解析要收 `2026-10-03` / `2026 10 03` / `2026/10/03` / `2026.10.03` / `10/3`；**不要因为少补零就报错** |
| **必须能清空** | MD3 专门讲 Clear 按钮，同时说"if it's not needed for your use case, **remove** the Clear button ... to reduce the number of tab stops" | 保留清空（"我设错了日期"是必需场景），但它是**唯一**的清空入口，不额外加 |
| **helper text 说明格式** | MD3："The helper text (below the text field) **should specify the date format**" | 控件下方常驻格式提示（`2026-10-03`），写在 helper 而不是 placeholder |

**"失焦才格式化"这条在本项目尤其要紧**：项目有中文输入法，`compositionstart/end` 期间绝不能动输入框的值——这与 `AGENTS.md` 记的命令面板 IME 闸门是同一个坑。

### 2.2 符号冲突的规避（重要）

**现有代码已经占用了 `#` 和 `@`**：`useQuickCapture.ts:19-49` 的 `detectType` 规定——

```ts
if (trimmed.startsWith("#")) return { type: "task", ... };      // # 开头 = 任务
if (trimmed.startsWith("@")) { /* @ + URL = 书签 */ }           // @ 开头 = 书签
// 其他 = 卡片
```

这是**行首前缀**，语义是"这条输入要创建什么类型的资源"。新语法里的 `#标签` / `@提及` 是**行内 token**，语义是"这条任务的属性"。两者会撞车：

```
#购物          ← 现状：创建一条名为"购物"的任务
#购物 #家务    ← 现状：创建名为"购物 #家务" 的任务
```

**裁决**：全局浮窗的**类型前缀仅在输入框第一个非空白字符处**生效，且**其后必须紧跟空白或行尾**才算前缀。规则表：

| 输入 | 判定 |
|---|---|
| `#` | 类型前缀（任务），标题为空 → 拒绝 |
| `#购物` | **类型前缀 + 标题"购物"**（保持现状行为，不破坏已有用户习惯） |
| `#购物 #家务` | 类型前缀（任务）+ 标题"购物" + 标签"家务" |
| `买 #牛奶` | 不在行首 → 任务（走默认 task 录入）+ 标题"买" + 标签"牛奶" |
| `@https://x.com` | 类型前缀（书签），保持现状 |
| `@bob 问下进度` | `@bob` **不在行首** → 提及 token；标题"问下进度" |
| `写周报 @bob` | 提及 token |

判定的实现口径见 §5 的 `parseCapture`。这条规则必须写进单测，因为它是向后兼容的分界线。

### 2.3 解析规则

**只在两处尝试匹配**，降低误报：

1. **行首**（第 0 个非空白 token 之后）—— 用于剥离全局浮窗的类型前缀
2. **整行任意位置**，但要求 token 前是**行首或空白**（`\s`），token 后是**空白或行尾**

规则 `买牛奶#加急` 中的 `#` 前面是汉字，不构成 token 分界 → **不解析**，整串留作标题。

| 规则 | 说明 |
|---|---|
| 标题 = 剥离所有已识别 token 后剩余文本的**空白归一化**结果 | `写周报   p1  ` → `"写周报"`；多空格折叠为单空格；不 trim 到空则**拒绝创建**（对应 [01](01-现状与问题.md) §6 那条"纯空格能过校验"的缺陷，在解析层就堵住） |
| token 顺序**不影响**字段 | `p1 #工作 写周报` 与 `写周报 p1 #工作` 等价。Todoist/RTM 都允许任意顺序（RTM 官方博客明确说"task name and due date should always come first, but you can include the below properties in any order after that"） |
| 同一符号重复出现 | 优先级**取第一个**（`!p3 !p1` → p3）；标签**全部保留**（`#a #b` → 两个标签）；时长**取第一个** |
| 未识别的 token | **静默留在标题里**，不报错、不高亮。例：`!high` 不是合法优先级 → 标题变成 `写周报 !high` |
| 标签名合法性 | `[\p{L}\p{N}_-]+`（Unicode 字母/数字/下划线/连字符），1–32 字符。不合法则整个 token 留在标题里 |
| 优先级大小写 | `!P1` = `!p1`；`!p5` 非法 → 留在标题里 |
| 时长语法 | `~(\d+(\.\d+)?)(m\|min\|h\|hr\|小时\|分钟)?`。裸数字按分钟。`~0` 非法（后端有 `>= 0` CHECK，但 0 分钟无意义） |
| 中文标签免转义 | `#工作` 直接可用，无需 `#%E5%B7%A5%E4%BD%9C` |

### 2.4 提及 `@` 的处置

`@bob` **本期只解析不落库**。理由：`user` 表存在且有用户名（测试账号 qa/qatest123），但"任务提及某人"牵出的是**通知与协作**问题——被提及的人要不要收到通知、能不能看到这条任务、越权时按 404 还是按无权限处理。这些是独立议题，混进本轮会让范围失控。

**落地口径**：解析出 `@name` 后**从标题里剥离**，存进 `task.description` 顶部的一行 `> 提及：@bob`（Markdown 引用块，渲染时是一条普通的提及样式）。这样解析行为与存储行为解耦——将来要加 `task_mention` 关联表，只需从这段文本回填，解析器不用改。

不解析也可以（`@bob` 留在标题里），**但那会让 `@` 符号毫无价值**，所以选择解析并落 Markdown。

### 2.5 交互契约

```
键                行为
─────────────────────────────────────────────
Enter            提交。创建成功 → 清空输入、第 2 层收起、**焦点留在标题框**
Shift+Enter      同上，但提交后不清空（连写多条时用）
↓ / 点击 [+]     唤出第 2 层（焦点仍在标题框）
Esc              收起第 2 层；已收起时清空输入（不清空前先失焦让值落定）
Tab              在第 1 层内**不移动焦点**（P3：两层之内不逃逸）
```

**提交后零打扰**：不弹模态、不跳转、不滚动物流。toast 提示"已创建"并在 2 秒后自动消失（沿用现有 `showToast`）。

**乐观更新**：先在本地列表插入临时任务（沿用 `TaskProvider.tsx:89-101` 的 `makeTemp` 模式），请求失败才回滚并 toast。这与项目既有的"列表写操作走乐观更新"约定一致（`AsyncView` 在 loading 时渲染骨架屏，refetch 会让列表闪一下）。

**连续录入**：提交后焦点必须回到标题输入框。连续录入 5 条应该是 5 次 `(输入, Enter)`，中间零鼠标操作。

## 3. 第 2 层：唤出的补充控件

由 `[+]` 唤出，**六个控件全部可选**，任何一个留空都不影响创建成功。

| 控件 | 类型 | 默认 | 说明 |
|---|---|---|---|
| 截止时间 | `datetime-local` | 空 | 落 `due_at`（新增列，见 [04](04-数据模型.md)） |
| 开始时间 | `datetime-local` | 空 | 落 `start_at`（新增列）。软约束，不阻塞 |
| 优先级 | `Select` 4 项 | 空（= p3 语义） | 落 `priority`（新增列） |
| 标签 | 已选标签为 chip，输入回车新增 | 空 | 写入 `task_tag` 关联表 |
| 预计时长 | `number` + 单位 | 空 | 落 `effort_estimate_minutes`（**已有列**） |
| 父任务 | `Select` | 空 | 落 `parent_task_id`（**已有列**） |

前五项与第 1 层的符号是**同一份状态的两种输入方式**。用户在第 1 层写了 `!p1`，第 2 层的优先级下拉同步显示 p1；反过来在下拉选了 p2，第 1 层的 `!p1` token 要**变回普通文字**。这层双向同步是 P3"披露"的核心——第二层不是第二份数据，是同一份数据的另一种视角。

**空值语义要区分**：

| 字段 | 空 = "未设置" | 能区分"未设置"与"显式清空"吗 |
|---|---|---|
| `due_at` | `NULL` | 需要。`UpdateTaskRequest` 用双层 `Option<Option<T>>`（`dto.rs:34-54` 已有此范式） |
| `priority` | `NULL` | 需要。`NULL` = p3 语义但"用户没表达过"；显式 `p3` 应当被尊重 |
| `effort_estimate_minutes` | `NULL` | 已有双层 Option |
| `parent_task_id` | `NULL` | 已有双层 Option |

`priority` 区分 `NULL` 与 `'p3'` 的意义：见 [05](05-排序与推荐.md) §2.2——未表达过优先级的任务，打分时按中性处理；用户显式选了 p3，说明他确实认为它"重要但不紧急"，应当给一个（很小的）正向偏置。

## 4. 收件箱语义

新建任务默认 `status = 'backlog'`（后端 `CreateTaskRequest` 就没有 `status` 字段，[01](01-现状与问题.md) §1），**不要求**任何其他属性。

对应 P6：这是收件箱，要能接住"想做的事"。下面是列表的默认视图排序（详见 [05](05-排序与推荐.md) §2）：

```
今天
  ────────────────────────────
  !p1  写周报            今天 15:00 截止   ⏱60m
      读 GS 论文         (无截止)               ⏱40m
  ────────────────────────────
即将到期（7 天内）
  ────────────────────────────
  p3   复查账单          逾期 2 天              ⏱30m
  ────────────────────────────
收件箱（无截止、无优先级）
  ────────────────────────────
      想做：整理照片
      想做：学做酸菜鱼
```

注意"想做"的那两条和"该做"的混在同一个收件箱里——Cultured Code 的原话是"如果你只录入该做的事，回看待办就会变成一件苦差"（**[官方]**）。

## 5. 解析器契约

纯函数，**前端本地执行，不调后端**。理由：录入要即时反馈，网络往返会让"回车即创建"的体感崩掉；而且解析规则是纯文本变换，放后端没有收益。

```ts
// web/src/domains/task/model/capture.ts

export interface CaptureResult {
  title: string;
  cleanTitle: string;              // 剥离 token 后归一化的标题（用于展示与创建）
  priority: TaskPriority | null;   // 'p1'|'p2'|'p3'|'p4'|null
  tags: string[];
  mentions: string[];
  effortMinutes: number | null;
  /** 未能解析、留在标题里的原文片段，用于第 1 层下方的提示 */
  unparsed: string[];
}

export function parseCapture(input: string): CaptureResult;
```

**可插拔**（P5 保留的余地）：内部按"前缀判定 → token 扫描"两段结构组织，将来要加 NLP，只需在 token 扫描前插入一个 `naturalLanguageParser` 阶段，返回它能吃掉的 token 区间，**调用方签名不变**。

**单测矩阵**（`capture.test.ts`，纯函数，node 环境）：

| 组 | 用例 |
|---|---|
| 前缀兼容 | `#x` `#x y` `#x #y` `@https://a.b` `https://a.b`（无前缀→卡片） |
| 优先级 | `!p1` `!P1` `!2`（=p2） `!p5`（不解析） `!p1 !p3`（取首） `!p1x`（不解析） **`p1`（无 `!`，不解析，留标题）** |
| 标签 | `#工作` `#a#b`（一个标签） `#a-b_c` `#a,b`（截到逗号） `#`（不解析） `买牛奶#加急`（不解析） |
| 时长 | `~60m` `~1.5h` `~2hr` `~90`（分钟） `~0`（不解析） `~abc`（不解析） |
| 提及 | `@bob` `@bob @alice` `a@b.com`（不解析，`@` 前是字母） |
| 顺序 | `!p1 #a 写周报` ≡ `写周报 !p1 #a` |
| 标题归一 | `写周报   !p1` → `写周报`；`!p1`（标题空）→ 拒绝；`   ` → 拒绝 |
| 组合 | `写周报 !p1 @bob #工作 15:00 周五 ~60m`（`15:00` 与 `周五` **不解析**，原样留在标题——标题行永不解析日期，P5） |

### 解析器与全局浮窗的整合

`useQuickCapture.detectType`（`useQuickCapture.ts:19-49`）改造为委托给 `parseCapture`：

```
detectType(input):
  1. 判定行首类型前缀（# 任务 / @ URL 书签 / 其余 卡片）  ← 保持现状语义
  2. 剩余文本交给 parseCapture 提取属性
  3. 卡片与书签走原有路径（不解析本任务的属性语法）
```

`#` 开头创建**任务**这条既有行为**不变**（[02](02-设计原则.md) P4：符号选定即锁定，不能因为新语法方便就改掉旧语义）。

## 6. 录入之外的"后添加"路径

P1 说"其余属性可后加"，那**后添加的入口在哪**？这决定了录入成本是否真的低。

| 场景 | 入口 | 交互 |
|---|---|---|
| 想给一条已有任务加标签 | 任务行内 | 悬停显示 `[标签]` 图标 → 点击展开 chip 输入 |
| 想改截止时间 | 任务行内 | 悬停显示 `[日期]` 图标 → 原生 `datetime-local` |
| 想设优先级 | 拖到看板某列 | **不**。看板列就是状态，与优先级是两个维度，混淆会更糟 |
| 想排进日历 | 日历上拖 | 从任务列表拖事件条到时间轴 → 建 `planned` 窗口（[06](06-日历视图.md) §6） |
| 一次性批量补属性 | 列表多选 | 勾选多条 → 批量设标签/优先级/截止（**本期不做**，记为后续项） |

**行内图标只在悬停/聚焦时出现**（`.taskItem:hover .taskInlineActions` / `:focus-within`），避免在密集列表里造成视觉噪音——项目已有 `TaskItem.tsx:58-99` 的操作区，沿用同样的显隐策略。

## 7. 验收标准

这一节是 [08](08-实现路线.md) 各阶段的验收依据，抄一份在这里。

| # | 标准 | 怎么验 |
|---|---|---|
| A1 | 空标题（纯空格/纯符号）无法提交 | 单测 `parseCapture` + 手测 |
| A2 | 输入 `写周报 p1 @bob #工作 ~60m` 按 Enter 后：标题为 `写周报`，优先级 p1，标签"工作"，时长 60，提及进 description | 单测 + 手测 |
| A3 | 提交后焦点仍在输入框，列表顶部已出现新任务 | 手测（DevTools 查 `document.activeElement`） |
| A4 | 连按 5 次 Enter 不需要任何鼠标操作 | 手测计时 |
| A5 | 第 1 层不出现任何 `required` 标记；第 2 层全部留空也能创建 | 手测 |
| A6 | `#购物` 仍创建名为"购物"的任务（向后兼容） | 回归测试 `quick-capture` |
| A7 | `买牛奶#加急` 整串成为标题，不产出标签 | 单测 |
| A8 | 第 2 层最多两层：从录入到任务详情不存在第三层披露 | 走查 |
