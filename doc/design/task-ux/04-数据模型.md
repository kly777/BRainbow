## 2. `task` 表的列变更

### 2.1 声明增量

改 `crates/db/src/schema/tables.rs` 的 `task` 表 DDL，**保持已发布 DDL 文本不被改写**（`AGENTS.md` 明令：老库的列是照声明文本逐字追加的）：

```sql
CREATE TABLE IF NOT EXISTS task (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    description TEXT,

    -- 结构关系
    parent_task_id INTEGER,

    -- 状态管理
    status TEXT DEFAULT 'backlog',
    completed_at TIMESTAMP,

    -- 精力估算
    effort_estimate_minutes INTEGER,

    -- 关联用户
    user_id INTEGER,

    -- 元数据
    created_at TIMESTAMP DEFAULT (strftime('%Y-%m-%dT%H:%M:%S+00:00','now')),
    updated_at TIMESTAMP DEFAULT (strftime('%Y-%m-%dT%H:%M:%S+00:00','now')),

    -- 新增：时间承诺（v24）
    start_at TIMESTAMP,
    due_at TIMESTAMP,
    priority TEXT,

    -- 外键约束
    FOREIGN KEY (parent_task_id) REFERENCES task(id),
    FOREIGN KEY (user_id) REFERENCES user(id),

    -- 检查约束
    CHECK (effort_estimate_minutes IS NULL OR effort_estimate_minutes >= 0),
    CHECK (priority IS NULL OR priority IN ('p1','p2','p3','p4')),
    CHECK (due_at IS NULL OR start_at IS NULL OR start_at <= due_at)
)
```

### 2.2 三个设计决定，逐条说明

**决定 A：`start_at` 与 `due_at` 分成两列，不合成一个"时间窗"。**

不合成是因为语义不同：`due_at` 是**承诺**（"这个时间之前要做完"），`start_at` 是**软偏好**（"我大概从这时候开始"）。两者的缺失含义不同（没填 due = 没有任何时间压力；没填 start = 随时可以开始），而合成一列会强迫用户区分"我打算什么时候做"和"我承诺什么时候做完"——这个区分在录入那一刻（正是最没耐心的时候）是无意义的负担。

约束只加了一条 `start_at <= due_at`：反了必然是录入错误，`CHECK` 兜住比 service 层校验更彻底（绕不过去）。注意 `due_at IS NULL OR start_at IS NULL` 前半段让"只填 start 不填 due"合法——这是常见情况。

**决定 B：`priority` 存字符串 `'p1'`…`'p4'`，不存整数。**

存字符串的理由：① 可读，`.sqlx` 快照与日志里直接看得懂；② 将来若要插入 `p0`（比 p1 更急）不需要改类型语义；③ 项目已有先例——`time_window.type` 存字符串 + `CHECK (type IN (...))`（`tables.rs:183`），口径一致。

存 `NULL` 而非默认 `'p3'` 的理由见 [03](03-录入模型.md) §3：`NULL` = "用户没表达过"，`'p3'` = "用户认为它重要但不紧急"。打分时要区别对待（[05](05-排序与推荐.md) §2.2）。**代价是**排序 SQL 里要写 `COALESCE(priority,'p3')`，这没问题。

**决定 C：不加 `NOT NULL` 的任何新列。**

P1 的数据库级体现：录入只要求标题，那就让数据库也允许除了标题之外的一切为空。

### 2.3 「升级 ≡ 新建」的自动覆盖

改完声明后，`db::tests::upgrade_path_reproduces_column_definitions` 会自动把三列删掉再 reconcile，与新建库逐列比对类型/NOT NULL/默认值/生成列。**这是声明驱动的，测试清单是推导的**——加列不需要在测试里登记任何东西（`AGENTS.md`「升级 ≡ 新建」节）。所以本期的 schema 变更**自动获得**这一层回归保护。

## 3. 标签：复用 `tag` 表

项目里已有三套标签方案：

| 表 | 特点 | 归属 |
|---|---|---|
| `file_tag`（`tables.rs:253-259`） | 自带 `name` + `user_id`，`UNIQUE(name, user_id)`；`idx_file_tag_name_unique` 改成**全局唯一**（v18 起，注释写明"标签全局共享：同名标签只允许一条"） | file 模块专用 |
| `tag`（`tables.rs:421-429`） | `name` + `user_id` + `created_at`，`UNIQUE(name, user_id)` | mem 模块专用（`mem_tag` 关联） |
| `bookmark_tag` | 关联表 | bookmark 模块专用 |

**决定：复用 `tag` 表 + 新建 `task_tag_rel` 关联表。**

```sql
CREATE TABLE IF NOT EXISTS task_tag_rel (
    task_id INTEGER NOT NULL,
    tag_id  INTEGER NOT NULL,
    PRIMARY KEY (task_id, tag_id),
    FOREIGN KEY (task_id) REFERENCES task(id) ON DELETE CASCADE,
    FOREIGN KEY (tag_id)  REFERENCES tag(id)      ON DELETE CASCADE
)
```

理由：
- `file_tag` 的 `name` 是**全局唯一**（`idx_file_tag_name_unique`），而 `tag` 表是 `UNIQUE(name, user_id)` **按用户唯一**。任务标签应按用户隔离——A 用户的"家"和 B 用户的"家"是不同标签。复用 `tag` 正确，复用 `file_tag` 会造成跨用户标签串味。
- 新建一张 `task_tag` 表会让三套并存，第四套更糟。
- `mem_tag`（`tables.rs:432-441`）就是完全同形的关联表，照抄它的形状（无 `id` 列、`PRIMARY KEY(task_id, tag_id)` 复合主键、两个 `ON DELETE CASCADE`），**包括删标签时级联清理**。

**代价要说清楚**：`tag` 表当前没有 `user_id` 索引（`tables.rs` 的 `user_id_index!()` 列表里没有它，见 [01](01-现状与问题.md) §6）。加进这个列表会让所有用户都受益，但要确认 mem 模块的 `tag` 查询不会被索引变更影响执行计划。本期**加**这个索引，理由是"标签按用户查"是三处共用的主查询路径。

## 4. 时间列必须登记

`time::TIME_COLUMNS`（`crates/db/src/schema/time.rs`）是**唯一**的时间列清单，有测试 `time_columns_cover_every_timestamp_column` 钉住：库里每个 TIMESTAMP 列都要在清单里，且 `trg_task_time_iso_{ins,upd}` 真的建得出来。

```rust
// crates/db/src/schema/time.rs 的 TIME_COLUMNS，追加一行
("task", "id", &["created_at", "updated_at", "completed_at", "start_at", "due_at"]),
```

**为什么这么较真**（`AGENTS.md` 原话）：老库的**列默认值改不掉**（SQLite 不能改列定义），历史上基线写过三种时间格式，老库与新库的默认值天然不同——这无害**当且仅当**写入会被触发器改写成规范格式。漏进清单的列会把默认值格式原样落库。

新加的 `start_at` / `due_at` 都会由应用层显式写入（`service.rs` 里用 `time_text::utc_now_iso()` 或前端传的 ISO 串），不走默认值。但**仍然要登记**：触发器还负责把"前端传来的 `2026-10-03T15:00:00Z`"（带 Z）归一成 `+00:00` 格式，而前端**一定会**这么传（`toISOString()` 的输出就是 Z 结尾）。

> 顺带确认既有登记：task 那一行已在 `time.rs:123`，是 `("task", "id", &["completed_at", "created_at", "updated_at"])`（`time.rs:133` 那行是 mem 的，别抄错）。本次只是往 task 行的数组里追加两个元素。

**漏登记的症状**：`due_at` 落库成 `2026-10-03T15:00:00Z` 而不是 `2026-10-03T15:00:00+00:00`，而 `--check` 的第 6 项（时间戳格式扫描）会报出来。`just deploy` 收尾那次自检会把它报成非致命告警——**所以这个错误会漏到生产才被发现**，务必先跑 `just sqlx-prepare` 前的迁移演练。

## 5. 索引

现状：`task` 与 `time_window` **都没有任何索引**（`tables.rs` 的 `user_id_index!()` 列表不含它们）。本期的查询模式全都要按 `user_id` 过滤，所以先补最基本的：

```sql
-- 归属过滤：所有列表查询都带 (?N IS NULL OR user_id = ?N)
CREATE INDEX IF NOT EXISTS idx_task_user          ON task(user_id);
CREATE INDEX IF NOT EXISTS idx_task_user_due      ON task(user_id, due_at);
CREATE INDEX IF NOT EXISTS idx_task_user_status   ON task(user_id, status);
CREATE INDEX IF NOT EXISTS idx_task_user_created  ON task(user_id, created_at DESC);

-- 建议算法：按用户取未完成任务
CREATE INDEX IF NOT EXISTS idx_time_window_user_type ON time_window(user_id, type);

-- 标签：两向查询（按任务取标签 / 按标签取任务）
CREATE INDEX IF NOT EXISTS idx_task_tag_rel_tag ON task_tag_rel(tag_id);
```

`idx_task_user_created` 覆盖现有全部 `ORDER BY created_at DESC` 查询（`repository/crud.rs:34`、`:67`），加了它现有查询就快一档。

`idx_task_user_due` 服务 [05](05-排序与推荐.md) 的建议查询（"取 7 天内到期且未完成的"）。

**`priority` 不建索引**：它是打分的输入因子而不是过滤条件，参与集合是"全部未完成任务"，走 `idx_task_user_status` 就够了。给一个低基数（4+NULL）列建索引是反模式。

`task_tag_rel` 的主键 `(task_id, tag_id)` 已覆盖"按任务取标签"；`idx_task_tag_rel_tag` 覆盖反向。

## 6. 与死表的冲突

`task_decomposition` 与 `task_time_allocation` 两张死表（[01](01-现状与问题.md) §4 缺口 A）**随本期一起删掉**。

**为什么现在删**：判定死表的依据是"全仓无任何代码读写，grep 仅命中 `tables.rs` 的 DDL 声明"；而因为不保留旧设计，删表成本就是**在 `legacy::TABLES` 加两行 + `SCHEMA_VERSION += 1`**（阶段 ① 生效）。既然下一次改 schema 就要走一遍真库演练，那顺手删掉比单开一次变更省事。

**动手前的唯一检查**：再跑一次 `rg -n 'task_decomposition|task_time_allocation'` 确认无遗漏。这是本轮唯一会造成不可逆数据损失的操作——而它们恰好是唯二"丢了也没人知道少了什么"的表。

`task_time_allocation(task_id, time_window_id, duration_minutes)` 的语义是"某个任务在某个时间窗里分配了多少分钟"——这恰好是排程需要的东西，但本设计用不上：

- 它的 `duration_minutes` 与 `time_window.start_time/end_time` **信息冗余**（时长可以从区间算出来）
- 建议算法**不落库**（P9），所以没有需要它承载的写入

**顺带记一笔，避免将来重新提起**："新设计要一张时长分摊表"这个想法很容易回来。答案是：那要等自动排程真的落库那天再讨论，而那天应该先问"**为什么 duration 要单独存，而不是从区间算**"。

## 7. 后端 API 契约变更

### 7.1 DTO

```rust
// src/modules/task/dto.rs

pub struct CreateTaskRequest {
    pub title: String,                    // 唯一必填（P1）
    #[serde(default)] pub description: Option<String>,
    #[serde(default)] pub parent_task_id: Option<i32>,
    #[serde(default)] pub effort_estimate_minutes: Option<i32>,
    // 新增
    #[serde(default)] pub start_at: Option<DateTime<Utc>>,
    #[serde(default)] pub due_at: Option<DateTime<Utc>>,
    #[serde(default)] pub priority: Option<TaskPriority>,
    #[serde(default)] pub tags: Option<Vec<String>>,   // 标签名数组，服务端 upsert
}

pub struct UpdateTaskRequest {
    // 已有字段不动
    #[serde(default)] pub start_at: Option<Option<DateTime<Utc>>>,   // 双层
    #[serde(default)] pub due_at: Option<Option<DateTime<Utc>>>,     // 双层
    #[serde(default)] pub priority: Option<Option<TaskPriority>>,    // 双层
    #[serde(default)] pub tags: Option<Vec<String>>,                // 整体替换
}
```

**双层 `Option` 的理由**：`Option<Option<T>>` 区分"不改"（`None`）与"清空"（`Some(None)`）。`dto.rs:34-54` 已有这个范式（`description` / `parent_task_id` / `effort_estimate_minutes` 都是），新字段沿用即可——这是 `UpdateTaskRequest` 已经建立的约定，不是新发明。

`tags` 用**整体替换**语义（PUT 而非 PATCH-on-collection）。理由：前端永远持有该任务的完整标签集（从 `GET /tasks/{id}` 拿），增量增删要多一次往返且容易与服务端状态不一致。

### 7.2 新增枚举

```rust
// src/modules/task/model.rs
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
#[serde(rename_all = "lowercase")]
#[sqlx(type_name = "TEXT")]
pub enum TaskPriority { P1, P2, P3, P4 }
```

与 `TaskStatus` 的差别：`TaskStatus` 实现了 `Decode`/`Type`（`model.rs:71-87`）因为 `query_as!` 需要；`TaskPriority` 若走 `query_as!` 同样需要这两个 impl，照抄 `TaskStatus` 的写法。同时照抄 `FromStr`（大写转小写容忍）与 `Display`。

> `model.rs:60-69` 那个 `impl From<String> for TaskStatus`（未知值回落 `Backlog`）**不要照抄**到 `TaskPriority` —— 优先级回落成 p3 会让"用户存了坏数据"和"用户选了 p3"变得无法区分，且 CHECK 约束已经在 DB 层拦了。

### 7.3 service 层新增校验

```rust
// TaskService::create / update 内新增
fn validate_time_range(start: Option<DateTime<Utc>>, due: Option<DateTime<Utc>>) -> Result<(), ServiceError> {
    if let (Some(s), Some(d)) = (start, due) {
        if s > d {
            return Err(ServiceError::InvalidInput("开始时间不能晚于截止时间".into()));
        }
    }
    Ok(())
}
```

DB 的 `CHECK` 已经兜住了，但 service 层校验的价值是**给用户可读的即时反馈**（`CHECK` 失败会变成一条 500 或一条难懂的 DB 错误文案）。这与项目既有的 `validate_title` / `validate_effort` 是同一个模式。

### 7.4 端点

| 端点 | 变化 |
|---|---|
| `POST /api/tasks` | DTO 加字段，无路由变化 |
| `PATCH /api/tasks/{id}` | DTO 加字段，无路由变化 |
| `GET /api/tasks` | 响应 `Task` 加 `start_at` / `due_at` / `priority` / `tags` |
| `GET /api/tasks/{id}/detail` | 同上（`TaskDetailResponse`） |
| `GET /api/tasks?sort=…` | **新增**排序参数，取值 `smart`（默认）\| `due` \| `created` \| `priority` \| `effort` |
| `GET /api/tasks/suggestions?from=…&to=…` | **新增**，纯读，见 [05](05-排序与推荐.md) §3 |
| `GET /api/tags?prefix=…` | **新增**，标签自动补全用（前缀查询 8 条） |
| 现有 20 条路由路径 | 全部不动 |

`sort=smart` 走新算法，其余取值映射到 SQL `ORDER BY`。默认从 `created_at DESC` 改为 `smart`——这是本设计对现有用户可见的**唯一破坏性变化**（列表顺序会变）。因为不保留旧设计，**不留 `?sort=created` 作为系统兜底**；`created` 仍作为用户可选的排序方式出现在下拉里。

**`status` 从裸 `string` 改成联合类型，本期做。** 它现在是 `api-types.ts:12` 的 `status: string`，也就是 `groupByStatus` 那种"未知状态静默丢弃"在类型上其实是**可表达的**——编译器不拦。收紧成 `TaskStatus` 之后，链路上的每一处 switch 都会在编译期暴露：`TaskList` / `TaskKanban` / `lib/task-group.ts` / `status-colors`。这四处的改造本来就是 S2–S3 重写要动的地方，所以这一步是顺带的。

## 9. 本期的 schema 变更检查清单

照 `AGENTS.md` 的顺序，一步步做：

```
1. 改 crates/db/src/schema/tables.rs          （task 三列 + task_tag_rel + 索引声明）
2. crates/db/src/schema/legacy.rs             （TABLES 追加两张死表，阶段 ① 生效）
3. crates/db/src/schema/time.rs               （TIME_COLUMNS 追加 due_at / start_at）
4. crates/db/src/schema/mod.rs                （SCHEMA_VERSION: 23 → 24）
5. cargo test                          （upgrade_path / time_columns 两个测试应自动覆盖）
6. 让本地库迁移                         （先迁移再写 SQL，见下）
7. 写引用新列的 SQL
8. just sqlx-prepare                    （.sqlx 快照一起提交）
9. cargo clippy --workspace --all-targets
```

**第 6、7 步的顺序不能颠倒**（`AGENTS.md` 明确：本机是**在线校验**编译，`.cargo/config.toml` 设了 `SQLX_OFFLINE=false` + `DATABASE_URL=sqlite:brainbow.db`）。先写引用新列的 SQL 会编译不过 → 跑不了迁移 → 库还是旧 schema → 死锁。应急才用 `SQLX_OFFLINE=true`。

注意 `-wal` 陷阱：换库文件前不连 `-wal`/`-shm` 一起删，陈旧 WAL 会被拼进新库（`cp` 出来的库 salt 相同，SQLite 的校验拦不住，实测拿到过"迁移完成 0.01s"的假象）。
