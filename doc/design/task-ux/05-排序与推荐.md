# 05 · 排序与推荐

> 状态：现行（已实现） · 代码基准：`main@48996cd7`（2026-10-22） · 最后核对：2026-10-22
>
> 目标：**让"先做哪件"从每天重复消耗的决策，变成系统回答。**
> 两条约束贯穿全文：**系统不自动落位**（P9）、**每条结果都要能说出理由**（P8）。
>
> 这两条不是品味偏好，是有实证支撑的取舍。**算法 aversion**（Dietvorst, Simmons & Massey 2015）证实：人看到算法犯错一次后，对它的信任掉得比对人犯错后更快——作者的解释说，因为人犯错时**看起来像是知道自己在做什么**，算法犯错没有这个信号。于是**自动排程哪怕偶尔好用，长期期望也是负的**；一次糟糕的自动落位就可能把用户永久推回手动，而手动正是 P9 要保留的东西。Timefold（OptaPlanner 作者自己的分支）把这讲得更直接：**"Optimization projects don't fail on math. They fail on adoption."** 详见 [07](07-调研附录.md) §3.9。

## 1. 两条不同的功能

必须先把它们分开，它们的输入输出、失败模式、验收标准都不同：

| | **排序**（Ordering） | **时段建议**（Slotting） |
|---|---|---|
| 回答的问题 | "先做哪件？" | "这几件大概能塞进哪天哪个空档？" |
| 输入 | 全部未完成任务 | 排序结果 + 日历已有安排 + 工作时段偏好 |
| 输出 | 一个有序列表 | 若干 `(task, start, end)` 建议 |
| 是否写库 | 否 | **否**（P9） |
| 端点 | `GET /api/tasks?sort=smart` | `GET /api/tasks/suggestions` |
| 失败的表现 | 顺序不合理但无损失 | 建议不可用（无可行空档）→ 必须诚实说"排不下" |

**不要把它们做成一个功能。** 排序每天都要用且必须永远有输出；建议只在用户主动打开"安排今天"时用且完全可以返回空。混在一起会导致建议算法的约束（要占空档）污染排序（排序不该关心日历）。

**两条的容错策略也不同，因为"错"的代价不同。** Kocielnik, Amershi & Bennett（CHI 2019）证实同样是 50% 准确率，**错误的类型**（误报 vs 漏报）会让用户的接受度显著不同。对应到这里：

- **排序**的漏报（该浮起来的任务沉下去了）几乎无害——用户仍然看到全部任务，只是顺序不同。误报（把一件无关紧要的顶到最前）会直接消耗信任。
- **建议**的误报（建议一个其实排不下的时段）会让用户白跑一趟，代价最高。

→ 所以**两处都偏保守**：排序用稳定的次级键兜底（§2.2），建议在低置信时走弱化样式而不是硬推（§3.1）。**宁可少给，不可假装**这句话有实证背书，不是谦虚。

## 2. 排序算法

### 2.1 形状：加权乘积

沿用项目内已验证的形状（`src/modules/mem/selection.rs:53-72` 的 `review_candidate_weight`）：

```rust
// src/modules/task/ranking.rs（新增文件）
pub fn task_score(task: &Task, now: DateTime<Utc>, ctx: &RankContext) -> Ranked
```

`Ranked` 不只是一个 `f64`，它**必须携带理由**（P8）：

```rust
pub struct Ranked {
    pub task_id: i32,
    pub score: f64,
    pub reasons: Vec<Reason>,   // 每项因子贡献多少、为什么
}

pub struct Reason {
    pub kind: ReasonKind,       // Overdue | DueSoon | Priority | Blocked | Aging | Inbox
    pub weight: f64,            // 该因子的乘数
    pub detail: String,         // 面向用户的中文短语，如 "逾期 2 天"
}
```

`reasons` 直接进 API 响应，界面照着显示。**没有 `reasons` 的排序不允许上线**——这是把 P8 变成可执行约束的方式。

### 2.2 四个因子

```
score = due_factor × priority_factor × blocked_factor × aging_factor
        （四者皆无信息时 fallback 到 created_at，保证全序）
```

四个因子都是**用户表达过的**信息。系统不引入用户没给过的东西——这是 P2 的延伸：不猜测，也就不用解释"我为什么猜这个"。

#### 因子 1：`due_factor` —— 截止时间（权重最高的自然因子）

参考 `mem/selection.rs:62-72` 的形状，但用**分段**而非连续函数——因为"逾期 2 天"和"逾期 20 天"在行动上不是一个量级的事，连续加权会让积压 20 天的任务永远压在新任务前面（这正是"陈旧任务饿死"问题）。

| 状态 | 值 | 理由文案 |
|---|---|---|
| 已逾期 | `2.0 + 0.5 × min(逾期天数, 14)` → 上限 **9.0** | "逾期 2 天" |
| 今天到期 | **2.5** | "今天到期" |
| 1–3 天内 | `2.0 - 0.3 × 天数` → 1.1 ~ 1.7 | "还剩 2 天" |
| 4–7 天内 | `1.0 - 0.1 × (天数-3)` → 0.6 ~ 0.7 | "还剩 5 天" |
| 8 天以上 | **0.4** | "8 月 20 日"（远期不占前排） |
| 无 due | **1.0** | 不写理由（无信息就是无信息） |

`mem/selection.rs:65` 用的 `(1 + days)^-1` 是连续衰减，在 due 上是合理的（记忆到期越近越该复习）。任务不同：任务有**完成**这个离散终点，远期任务今天做和 5 天后做没有本质区别，所以远期应该**塌缩**到常数而不是持续衰减。

#### 因子 2：`priority_factor` —— 手动优先级

| priority | 值 | 理由文案 |
|---|---|---|
| `'p1'` | **2.0** | "标为 p1" |
| `'p2'` | **1.5** | "标为 p2" |
| `'p3'` | **1.15** | "标为 p3" |
| `'p4'` | **0.8** | "标为 p4" |
| `NULL` | **1.0** | 不写理由 |

两个刻意的决定：

**`NULL`（1.0）落在 p3（1.15）与 p4（0.8）之间。** P8 说过"不能把没表达过的和表达过的混为一谈"，但打分是另一回事：未设优先级的任务若按 p3 算，会让所有未设优先级的任务系统性略微上浮，压过真正标了 p4 的用户决策。所以让它落在中间偏下。

**p1 的 2.0 低于"逾期 9.0"。** 这不是笔误，是刻意的：手动优先级是**用户对任务的认知**，逾期是**客观事实**。当用户标了 p1 但它已经逾期一周，逾期应该压过优先级——这与"逾期的 p4 排在未逾期的 p1 前面"一致，也与 `mem/selection.rs:221` 那个测试表达的直觉一致（加权策略确实比纯 due 排序更早暴露难项）。

#### 因子 3：`blocked_factor` —— 依赖阻塞

`task_dependency`（`task/service.rs:138-155`）已存在但无环检测，所以计算可达性时要**防御性限制深度**（见 §2.5）。

| 状态 | 值 | 理由文案 |
|---|---|---|
| 前置依赖全部完成 | **1.0** | 不写 |
| 有未完成的前置依赖 | **0.15** | "等 X 完成" |
| **检测到循环** | **0.1** | "依赖成环" |

`0.15` 而不是 `0`：完全归零意味着这类任务从"今天"列表里彻底消失，用户会以为它丢了。用户需要看到它、需要去解掉那个环，只是**不该现在做它**。

`0.1` 比 `0.15` 更低：成环是一个**数据错误**，排序器要把它压到最后并把"依赖成环"这个事实推给用户（顺带暴露了 `task/service.rs:138-155` 那个缺环检测的缺陷）。同时建议在 task 模块补上环检测，让这类数据进不来。

#### 因子 4：`aging_factor` —— 陈旧度

一个 backlog 里躺了三个月的任务，和昨天建的，放在一起时前者该被看见。GTD 的收件箱需要定期被清空，否则就是垃圾桶（**[官方]** 口径：澄清是一个有独立仪式的活动）。

| 停留天数（未完成） | 值 | 理由文案 |
|---|---|---|
| < 7 天 | 1.0 | 不写 |
| 7–30 天 | `1.0 + 0.1 × (天数-7)/23` → 最高 1.1 | "在收件箱躺了 20 天" |
| > 30 天 | **1.15** | "在收件箱躺了 60 天" |

上限设得很低（1.15）是有意的：`aging` 是**很弱的**信号。让一个躺了 60 天的 p4 靠 aging 浮到前面会违背用户明确的 p4 标记。它只用来在"都没有 due 和优先级"时打破平局。

#### 无信息时的次级排序（P2 冲突的缓解）

[02](02-设计原则.md) 的 P6/P8 冲突裁决里说过：无 due 无优先级的任务占多数时打分会失效。四因子全部为 1.0 时分数是平局。

**解决办法不是让分数带随机噪声**，而是加一组**只用于打破平局的稳定次级键**：

```
1. status: 'active' 优先于 'backlog'        （用户已经动手的，先做完）
2. updated_at DESC                          （最近碰过的优先）
3. created_at ASC                           （最早进的收件箱优先 —— GTD 纪律：先进先清）
4. id ASC                                   （最终保证全序，可测）
```

`created_at ASC` 是关键那条：GTD 的收件箱纪律本身就是先进先出（**[官方]** p.27："Do not put clarified items back into the inbox"）。这让"打字机录入 20 条"的任务按录入顺序被依次消费，而不是随机。

第 4 条 `id ASC` 保证**全序**——没有它，两条同分任务的相对顺序取决于 SQL 的执行计划，那不可测也不可解释。

### 2.3 完整示例

输入（现在时间 2026-10-02 09:00）：

| 任务 | due | pri | 状态 | 依赖 | 建于 | due_f | pri_f | blk_f | age_f | score |
|---|---|---|---|---|---|---|---|---|---|---|
| 写周报 | 10-02 15:00 | p1 | backlog | 无 | 09-20 | 2.5 | 2.0 | 1.0 | 1.03 | **5.15** |
| 复查账单 | 09-30 | p3 | backlog | 无 | 09-15 | 4.0 | 1.15 | 1.0 | 1.08 | **4.97** |
| 读 GS 论文 | 无 | NULL | backlog | 等"写周报" | 09-25 | 1.0 | 1.0 | 0.15 | 1.03 | **0.15** |
| 交物业费 | 10-20 | p4 | backlog | 无 | 09-01 | 0.4 | 0.8 | 1.0 | 1.15 | **0.37** |
| 整理照片 | 无 | NULL | backlog | 无 | 08-01 | 1.0 | 1.0 | 1.0 | 1.15 | **1.15** |

排序结果：

```
1. 写周报     5.15   今天到期 · 标为 p1
2. 复查账单   4.97   逾期 2 天 · 标为 p3
3. 整理照片   1.15   在收件箱躺了 60 天
4. 交物业费   0.37   8 月 20 日 · 标为 p4
5. 读 GS 论文 0.15   等「写周报」完成
```

四条可验证的排序性质（写成单测）：

| 性质 | 断言 |
|---|---|
| 逾期压过优先级 | `rank(逾期p4) < rank(未逾期p1)` |
| 阻塞项沉底但可见 | 阻塞任务分数 > 0，且 `rank(阻塞) > rank(任一未阻塞)` |
| aging 不压过显式 p4 | `rank(躺60天的p4) > rank(无信息的p2)` |
| 打平走次级键 | 两条同分任务按 `created_at ASC` 排 |

### 2.4 分数的量纲问题

`f64` 分数相乘的经典毛病：**溢出与精度**。四因子相乘，本设计的最大乘积是 `9.0 × 2.0 × 1.0 × 1.15 ≈ 20.7`，最小 `0.4 × 0.8 × 0.1 × 1.0 = 0.032`。**量级完全可控，不会溢出**（`f64` 溢出要 >1.8e308）。

但有一个真实风险：**浮点相等判定**。项目在 `main.rs` 顶部有 `deny(float_cmp)` 的 lint 门禁（`AGENTS.md` 明确列出 `float_cmp`），所以**不能写 `if a.score == b.score`**。

排序必须用**部分比较**：

```rust
// 不用 == 判等：把"是否需要次级键"编码进返回值
candidates.sort_by(|a, b| {
    b.score.partial_cmp(&a.score)
        .unwrap_or(std::cmp::Ordering::Equal)     // NaN 不该发生，但 total order 不能 panic
        .then_with(|| status_rank(a).cmp(&status_rank(b)))
        .then_with(|| b.updated_at.cmp(&a.updated_at))
        .then_with(|| a.created_at.cmp(&b.created_at))
        .then_with(|| a.id.cmp(&b.id))
});
```

`partial_cmp` 在有 `NaN` 时返回 `None`，`unwrap_or(Equal)` 让它退化成"当作相等，交给次级键"——**这正是想要的降级行为**，且不违反 float_cmp 门禁（`partial_cmp` 不是 `==`）。

### 2.5 数据质量：防御性处理

`task_dependency` **无环检测**（[01](01-现状与问题.md) §4 缺口 A），所以 A→B→A 能写进库。计算 `blocked_factor` 时必须防御：

```rust
// 依赖可达性：限制深度，避免成环时无限递归
const MAX_DEP_DEPTH: usize = 16;   // 与 time_window 的 expand_between 上限 500 同类思路
```

深度超限 → 判定为"依赖成环"（因子 0.1），**不是**判定为"未阻塞"。

**本期同时给 `task_dependency` 补上环检测**（`task/service.rs:138-155` 现在只拦自环），照 `check_circular_parent`（`service.rs:311-325`）的现成写法。这是数据层修复，不是 UX 特性，但缺了它排序器就得一直防御。

### 2.6 SQL 落地

排序在**应用层**做，不在 SQL 做。理由：`blocked_factor` 需要递归可达性、`aging_factor` 需要天数计算、`reasons` 需要逐项构造——用 QueryBuilder + 内存排序更直白，也更容易写单测。

```sql
-- 取候选：归属过滤 + 未完成状态
SELECT * FROM task
WHERE (?1 IS NULL OR user_id = ?1)
  AND status IN ('backlog', 'active')
ORDER BY updated_at DESC
LIMIT ?2
```

`status IN ('backlog','active')` 是**唯一在 SQL 里的过滤**。注意不能写 `status != 'completed' AND status != 'archived'` —— `groupByStatus`（`lib/task-group.ts:41-42`）把空串/undefined 归入 backlog，而 DB 侧 `status` 虽可空（无 NOT NULL）但有 `DEFAULT 'backlog'`，实际不会为空。用白名单而非黑名单，与"未知状态不该进排序"的语义一致。

分页：现有 `fetchAllTasks` 最多 10 页 × 100 条（`api-funcs.ts:10-13`）。排序后分页，**页内稳定**（次级键保证）——翻页不会看到重复或跳过的任务。

## 3. 时段建议算法

### 3.1 输出形状

```rust
// GET /api/tasks/suggestions?from=2026-10-02&to=2026-10-08
{
  "suggestions": [
    {
      "task_id": 42,
      "title": "写周报",
      "start": "2026-10-02T14:00:00+00:00",
      "end":   "2026-10-02T15:00:00+00:00",
      "effort_minutes": 60,
      "reason": "今天到期 · 标为 p1",
      "score": 5.15,
      "confidence": "high"     // high | medium | low
    }
  ],
  "unscheduled": [
    { "task_id": 51, "title": "读 GS 论文", "reason": "等「写周报」完成" }
  ],
  "capacity": {
    "total_minutes": 1800,      // 区间内工作时段总容量
    "used_minutes": 900,        // 已被 planned/actual 占用
    "suggested_minutes": 150    // 本次建议占用
  }
}
```

`unscheduled` 数组是**诚实的关键**（P10 的失败模式）。三类进不了建议：

| 原因 | 文案 |
|---|---|
| 依赖未解除 | "等「X」完成" |
| 区间内容量已满 | "这段时间排不下了" |
| 区间内在 due 之后 | "截止日期在这段时间之外" |

**返回空数组 + 原因，永远不返回一个塞满的建议集。** 自动排程的经典失败就是"日历填满"，而一个诚实的"排不下"比一个把周二塞满的算法有用得多。

### 3.2 输入

三样，缺一不可（P10）：

```rust
pub struct SlotContext {
    /// ① 已有硬占用：planned 与 actual 都算
    pub busy: Vec<(DateTime<Utc>, DateTime<Utc>)>,
    /// ② 用户工作时段偏好
    pub working_hours: WorkingHours,
    /// ③ 排序后的候选任务
    pub candidates: Vec<Ranked>,
    /// 各任务的 due（用于校验建议不越过承诺）
    pub deadlines: HashMap<i32, Option<DateTime<Utc>>>,
}
```

`WorkingHours` 是**新增的用户设置**（存 `app_settings` 表，走既有的 `app_settings` 机制）：

```rust
pub struct WorkingHours {
    /// 一天里的工作区间，本地时间。默认 09:00-12:00 + 14:00-18:00
    pub ranges: Vec<TimeRange>,
    /// 一周里的工作日。默认周一至周五
    pub weekdays: Vec<u8>,       // 1=周一 .. 7=周日（与 time_window.by_weekdays 同约定）
    /// 单个任务的建议时长上限（分钟）。默认 120
    pub max_slot_minutes: i32,
}
```

**为什么必须有这个设置**：不设默认就会建议出"凌晨 3 点写周报"——技术上不违反任何约束，实用上完全不可用（[02](02-设计原则.md) P10：已知失败模式是方案不可用）。这是"约束不全导致建议不可用"的直接例子。

时区：设置存**本地时间**的钟点（因为"我 9 点开始工作"说的是钟点不是 UTC 时刻），落库时用当前时区解释。项目的时间存储统一是 `+00:00`（`time_text`），所以 `WorkingHours.ranges` 要存时区偏移或约定用服务端配置时区。**本期约定：存本地钟点字符串，用 `.env` 的时区解释**（记为已知限制，见 §6）。

### 3.3 算法

贪心装箱，按 score 降序。

**为什么不引 OR-Tools。** 装箱是 NP-hard，但更关键的是**在线/离线之别**：在线装箱只能对"已知的未来"做决策，而个人日程里未来任务**永远不完全已知**（用户还没录入下周要做的事，任何求解器都无从得知）。OR-Tools CP-SAT 自己的定位是 **"based on feasibility rather than optimization"**，而它文档里的排程示例——护士排班、班次、工厂——**全部是多主体资源调度**（[07](07-调研附录.md) §3.9）。个人日程是单主体的在线问题，用不上那套。

**为什么贪心足够。** 理由是**用户会点掉不对的建议**——采纳是一次点击，不采纳零成本。求解器的最优性在这个交互模型下换不来对应收益，却要换来一个不可解释的黑箱，而不可解释正是 R1 风险的核心。

**"可行"比"最优"重要得多。** Timefold 把它写成 "**80% feasible is 100% useless**"：一份不可执行的排期毫无价值。所以本算法的验收标准是"**每条建议都真的落在空闲集内**"（第 2 步扣减、第 3.d 步从离散化后的空闲集里取），不是"总时长最大化"。

**一个佐证**：Google 日历的"查找会议时间"（Find time）常被当作"日历软件的排程算法"来举例，但它的官方文档把问题定义得很窄——**最多比较 50 位邀请对象的空闲情况，且要求对方已共享日历**（[官方文档](https://support.google.com/calendar/answer/6294878)）。也就是说它是**多主体**求交集问题，与本设计的单人任务装箱不同量级。**连 Google 都是为多人场景才动用约束求解的**，单人场景用贪心是够的。

```
输入: busy 区间集, working_hours, candidates(按 score 降序), deadlines
输出: suggestions[], unscheduled[]

1. 空闲集 ← 从 working_hours 展开出 [from, to] 内的所有工作区间
2. 空闲集 ← 空闲集 减去 busy（按半开区间 [start, end) 相减）
3. 对每个 candidate(按 score 降序):
   a. 时长 ← candidate.effort_minutes
      · 缺失 → 估一个：min(60, 标题长度 × 3 分钟)，且 confidence = "low"
      · 超过 max_slot_minutes → 截断到上限，confidence 降为 "medium"
   b. 若 candidate 被阻塞 → 跳过，记入 unscheduled("等 X 完成")
   c. 若 candidate 有 due 且 due < 区间开始 → 跳过，记入 unscheduled("截止日期在这段时间之外")
   d. 找空闲集中最早的、长度 ≥ 时长 的连续段（15 分钟对齐）
   e. 找不到 → 跳过，记入 unscheduled("这段时间排不下了")
   f. 采纳 → suggestions.push(...)，并从空闲集扣掉这一段
4. 返回
```

**第 3.d 步的 15 分钟对齐**：所有建议的开始与结束都对齐到 `:00/:15/:30/:45`。理由：人安排时间的粒度就是 15 分钟，落到 `14:07` 这样的建议在界面上没法用。空闲集本身要按 15 分钟**离散化**（切成一格一格的 slot），这样"找连续的 N 格"就是简单的滑窗。

**不做的事**：不拆跨午休的段（若一个任务时长 150 分钟而空闲只有 90+60 两段，不建议跨午休拼起来——用户会自己决定）。因为 greedy 从早到晚扫，第一个"连续 N 格"必然落在同一段内。

**`confidence` 的口径**（界面上要显示，见 [06](06-日历视图.md) §4）：

| 等级 | 条件 |
|---|---|
| `high` | 有明确 due 或显式优先级，且时长是用户给的 |
| `medium` | 时长被 `max_slot_minutes` 截断，或 due 在 7 天以上 |
| `low` | 时长是**估的**（用户没填 `effort_estimate_minutes`） |

`low` 的建议在界面上用虚线边框——"这只是个占位"。

**`low` 走弱化样式而不是直接隐藏**，这是被 Kocielnik et al. (CHI 2019) 的错误类型结论倒逼的取舍：漏报（该建议时没建议）会让用户以为"系统坏了"，误报（建议了一个假的空档）会浪费一次真实时间。两者都罚，**显式标注的低置信建议选漏报**——它至少让用户看见系统在哪儿不确定，而隐藏不会。代价是界面上会有看起来不可靠的块，所以它必须比真实事件更淡（[06](06-日历视图.md) §5.3）。

**但绝不能因为"可能有价值"就强推**：`busy` 集合看不到外部日历（[06](06-日历视图.md) §7），所以建议出的"空档"在用户真实世界里可能是会议。**这时正确做法是收紧文案（"基于你已安排的时段"）而不是提高置信度**——同一篇研究说**事先校准期望**能提高接受度，文案就是校准的手段。

### 3.4 循环窗口的处理

`time_window` 支持递归（`recurrence_freq` / `recurrence_interval` / `recurrence_by_weekdays`）。建议算法读 `busy` 时**必须展开循环**，否则一个每周重复的窗口只挡住基线那一次，后面几周的建议会直接压在它上面。

复用现成的 `TimeWindow::expand_between`（`time_window/model.rs:163-240`）。注意两个已知的坑（[01](01-现状与问题.md) §3）：

1. **上限 500 段**（`task/service.rs:217-226` 就是这么用的）。建议算法要用更小的上限（**52 段**，够一年的周视图）并在超限时**记一条告警**而不是静默截断。
2. **月度的注释与行为不一致**（注释说跳过该月，测试 `model.rs:486-506` 证明是钳制到月末）。建议算法里不能依赖注释。

### 3.5 与 `feasible` 的关系

现有的 `feasible`（可行时段）窗口是**用户手工声明的**"这几天我大概有空"。建议算法**不读** `feasible`——

- 读它会让语义混乱：`feasible` 是"我能做这件事的时段"，`planned` 是"我打算做"，`actual` 是"我做了"
- `busy` 只取 `planned` + `actual`（硬占用），`feasible` 是软信息
- 但**读它有一个好处**：如果用户已经声明了 `feasible`，建议应该优先落在那里（用户已经表达过偏好）

**决定：`feasible` 不参与 `busy`，但作为软偏好提升候选段的排序。** 落位在 `feasible` 内的建议 `confidence` 升一档，理由文案加"在你标记的可做时段内"。这个语义要在 `Reason` 里新增一个 `InFeasible` 类型。

C001 约束（`planned ⊆ feasible`，`task/service.rs:260-268`）**对建议不适用**——因为建议不写库。但如果用户采纳建议后前端去建 `planned` 窗口，而那个窗口不落在任何 `feasible` 段内，**C001 会拒绝**。

这是个真实的交互断裂。三个选项：

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 采纳时自动建配套 `feasible` | 用户采纳建议 → 同时建一个同区间的 `feasible` 窗口 | 污染用户的 `feasible` 语义（那个字段是"我空闲"，不是"我打算"） |
| B. 放宽 C001 | 去掉"planned 必须 ⊆ feasible"，改成警告 | 动既有约束，影响所有手工建窗口的路径 |
| C. 采纳时提示 | 前端检测到区间不在任何 `feasible` 内时，弹一次确认"这段时间不在你标记的可做时段内，仍要安排吗？" | 每次采纳多一次点击 |

**选 C。** 理由：A 污染用户数据，B 动的是既有校验（本轮不该动，回归风险高），C 只在真正冲突时出现一次且给出了足够信息。多数情况下工作时段偏好（`WorkingHours`）本身已经覆盖了 `feasible` 的意图，所以 C 很少触发。

## 4. 可解释性

P8 的落地。三处都要显示理由：

| 位置 | 显示什么 |
|---|---|
| 列表每行 | 最高贡献的那一条理由（`reason` 字段），不做完整因子展开 |
| 建议列表 | 全部理由 + 时段 |
| 建议的 tooltip / 展开 | 完整因子分解（`reasons` 全量） |

`Reason.detail` 的文案是**面向人的**，不是面向开发者的：

```
✓ "今天到期 · 标为 p1"        ← 列表行，紧凑模式
✓ "逾期 2 天 · 标为 p3"
✓ "在收件箱躺了 60 天"
✓ "等「写周报」完成"          ← 阻塞原因要指名被阻塞对象
✓ "依赖成环"                  ← 数据错误，要能被看见
```

不要写成 `"due_factor=2.5 × priority_factor=2.0"`。因子名可以出现在展开视图里，但默认视图只说人话。

**中文文案要含具体数字**（"逾期 2 天"而不是"已逾期"），因为用户要用这个数字做判断。

**"可解释"不是加个 info 图标就完事。** Liao, Gruen & Miller（CHI 2020）*Question Bank* 的方法是**不要凭空设计一个解释器**，而是先枚举用户会问的问题，再决定哪些值得答。对本设计，那个问题清单是：

| 用户会问 | 答案在哪 |
|---|---|
| "为什么是它排第一？" | 列表行的 `reason`（最高贡献因子，常驻） |
| "我这样标优先级有用吗？" | 排序**根本不用**优先级之外的猜测；factor 分解在展开里 |
| "它为什么被建议到周三下午？" | 建议块的 `reasons` 全量 + 时段 |
| "为什么这条没被建议？" | `unscheduled` 数组 + 理由（不是静默丢弃） |
| "它为什么排这么后？" | 排序把**所有**未完成任务都列出来，拖到底也能看到 |
| "这个系统知道我什么？" | 文案："基于你已安排的时段"（期望校准） |

Amershi et al.（CHI 2019）18 条 XAI 指南里有两条正好对应：**只解释系统能力范围内的事**（所以不解释"为什么推荐"——本系统不学用户偏好）、**按用户类别定制解释**（所以因子分解按"这条原因属于哪类"给出不同粒度，而不是所有人都看全量公式）。

## 5. 降级路径

每个环节都要有明确的失败行为：

| 环节 | 失败 | 降级 |
|---|---|---|
| 打分 | `due_at` 格式坏 | 视作 `NULL`，不报错（`due_factor` 回到 1.0） |
| 打分 | 依赖图成环 | `blocked_factor = 0.1`，理由"依赖成环" |
| 打分 | 深度超 16 | 同上 |
| 排序 | 分数全平 | 走次级键（§2.2），`id ASC` 兜底保证全序 |
| 建议 | 无工作时段设置 | 用默认值（09:00–12:00 + 14:00–18:00，周一至周五） |
| 建议 | 空闲集为空 | 返回 `suggestions: []` + `unscheduled` 全部注明"这段时间排不下了" |
| 建议 | 任务无时长 | 估一个（标题长度 × 3，上限 60 分钟），`confidence: low` |
| 建议 | 循环窗口 > 52 段 | 截断 + 记告警（`tracing::warn!`），不静默 |
| 建议 | 区间超过 90 天 | 拒绝，返回 400（避免大范围展开循环窗口） |

**降级的共同原则**：宁可少给，不可假装。返回空数组 + 明确原因，好过一个塞满的建议集。

## 6. 已知限制（写明而不是掩盖）

| 限制 | 影响 | 记为 |
|---|---|---|
| `WorkingHours` 存本地钟点，用服务端时区解释 | 跨时区用户会看到偏移 | 后续项（需要存时区偏移或用用户设置里的时区） |
| 贪心装箱不是全局最优 | 可能有更优排法 | 刻意取舍，见 §3.3（"可行"优先于"最优"） |
| **时间盒自身会坍塌** | 用户估的时长系统性偏乐观，于是日历越排越满、越满越排不下 | 规划谬误（Kruger & Evans 2004）是已确认的认知偏误；本期不学预估，但这解释了为什么 `confidence` 必须诚实 |
| 时长缺失时按标题长度估 | 猜得不准 | `confidence: low` + 虚线边框提示 |
| 不做自然语言日期录入 | 相比 Todoist 少一点便利 | P5 刻意取舍 |
| 依赖无环检测（本期会补） | 排序器必须防御 | §2.5 |
| 不处理"任务的实际耗时 vs 预估"学习 | 建议的时长会一直不准 | 后续项（`actual` 窗口的长度是天然的反馈信号） |
| **排序一旦错一次就可能永久失去信任** | 用户的信任衰减快于对人犯错 | 算法 aversion（Dietvorst et al. 2015）。这是 R1，也是 P9 存在的理由。缓解见 §1 与 §4 |

倒数第二条其实是个有价值的后续方向：`time_window` 的 `actual` 类型记录了"我实际做了多久"，与 `effort_estimate_minutes` 对比就能知道用户的预估偏差。**但本期不做**——它需要样本量积累，且属于"自动调整"而非"给建议"，跨过了 P9 的线。

**最后要老实说的一句**：本设计在这个领域**没有**自己的实证。它是对已有产品与公开研究的整理与取舍，而"可解释的自动排序能否被个人用户长期信任"这个问题，**至今没有人给出过可靠答案**（[07](07-调研附录.md) §6）。所以 [08](08-实现路线.md) 的 R1 给了明确的退出判据——**上线后如果用户反复切回 `created` 排序，就把 smart 降为可选，而不是加更多规则去抢救它**。
