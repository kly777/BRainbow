# 06 · 日历视图

> 状态：现行（已实现） · 代码基准：`main@48996cd7`（2026-10-22） · 最后核对：2026-10-22
>
> 目标：**月网格做全局概览，周/日时间轴承接排期与拖拽。**
> 视觉一律走项目既有令牌（`web/src/shared/styles/tokens.css` 的 `--t-*` + `web/src/app/global.css` 的 `--radius-*` / `--space-*`），本篇不发明新令牌（P12）。
> 键位、触摸目标、拖拽反馈遵循 W3C WCAG / WAI-ARIA APG / Apple HIG，出处见 [07](07-调研附录.md) §3。

## 1. 现状与目标

现状（[01](01-现状与问题.md) §3）：只有月网格，日期格内纵向堆叠文本行，无时间轴、跨日只落起始日、点事件无反应、颜色只按 `window_type` 三色而 `status` 未被使用、无"回到今天"、补位格 key 月份未补零。

| | 月网格 | 周时间轴 | 日时间轴 |
|---|---|---|---|
| **回答** | 这个月有哪些事 | 这周怎么排 | 今天怎么排 |
| **主用途** | 回顾、发现负载 | **排期主场景** | 执行当天 |
| **粒度** | 天 | 15 分钟 | 15 分钟 |
| **有建议** | 只显示数量徽标 | 显示建议块（虚线） | 显示建议块（虚线） |
| **可拖拽** | 否 | 是 | 是 |

三者**共享同一份数据与选中态**：在周视图点一个事件 → 切到日视图它仍高亮；从月视图点某天 → 切到周视图定位到那天。

**默认落在哪个视图？** 现状 `TaskPanel.tsx:37-52` 的 `right` 参数默认是 `calendar`（月网格）——当前实现见 `web/src/domains/task/TaskWorkspace.tsx` 与 `view/useTaskWorkspace.ts`。改成**周视图**为默认，理由：排期是本设计的主线（P9/P10），而月网格擅长的是"回顾"——回顾不必是默认视图。URL 参数保留 `right=month|week|day` 三值，缺省 `week`。

## 2. 视图切换的控件位置

现状是一个 `FilterGroup` 放在右栏顶部（`TaskPanel.tsx:37-52`），选项是"日历 / 依赖图"。

改成**两个维度分离**，并且**把工具条收敛到 5 个常驻控件**：

```
┌─ TaskToolbar ────────────────────────────────────────────┐
│  [列表 | 看板]  搜索…   录入框…                      [+]  │
├──────────────────────────────────────────────────────────┤
│  [月 | 周 | 日]   排序: 智能 ▾   [筛选 ⚙]      回到今天   │
├──────────────────────────────────────────────────────────┤
│                    日历主体                               │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

**收敛掉了什么，为什么**（P3 的判据同样适用于工具条——NN/g 说"每个表单项都在消耗解释—回忆—格式化三重成本"，控件也是表单项）：

| 控件 | 处置 | 理由 |
|---|---|---|
| **筛选 ▾** + **标签 ▾** | **合并成一个「筛选 ⚙」**，弹出面板里放全部条件 | 两个都是"低频打开、用完即关"的下拉，并排摆着只是占宽度。面板顶部显示**活动条件的 chip**（如 `状态=进行中 ×`），所以"筛选开着"永远看得见 |
| **[月 \| 周 \| 日]** | **保留常驻** | 当前粒度是**信息**不是命令——用户必须随时知道自己在看哪一层 |
| **排序: 智能 ▾** | **保留常驻，且当前值直接印在按钮上** | 排序决定用户看到的每一行，同属信息类。默认"智能"两个字要一直看得见 |
| **回到今天** | **保留常驻** | 翻到远处之后没它回不来（现状 `changeMonth` 只有 `±1`，`useTaskCalendar.ts:34-38`）。这是最低成本的可用性修复 |
| **建议 ☑**（网格右上角） | **保留常驻** | P9 的第二层保险，"不采纳也是一种操作"。它是图层开关，不是筛选 |

**筛选面板的内容**（全部为空时显示"无筛选条件"）：

```
┌ 筛选 ────────────────────────────┐
│ 状态      [全部 ▾]                │
│ 标签      [#工作 ×] [+ 添加]       │
│ 优先级    [全部 ▾]                │
│ 截止      [不限] ~ [不限]          │
├───────────────────────────────────┤
│ 活动：状态=进行中  ×   标签=工作 × │
│              [清空全部]            │
└───────────────────────────────────┘
```

> **为什么「标签」要进筛选面板而不是留在工具条**：它是筛选条件里最高频的一个（按项目/领域看任务），但**它本身也是信息**——用户常需要知道"我现在看的是不是只含 #工作"。解法是**活动 chip 常驻在按钮旁**，所以信息不丢，占位不占。

**"回到今天"是新增的**——现状只能 `±1` 翻月。

"依赖图"从 `FilterGroup` 里移出去，独立成一个 tab（与日历平级），因为 DAG 与日期无关，混在日历粒度选择器里是概念错误。

**清单与看板模式下**少了粒度与"回到今天"，多了列表/看板切换——所以任一时刻屏幕上**不超过 5 个**工具条控件。

## 3. 月网格

### 3.1 保留与改造

| 现状 | 处置 |
|---|---|
| 7 列周日起始 | **改为"设置项 + locale 默认"**（见下） |
| 14 个表头（7 全 + 7 简）CSS 切可见性 | **保留**（表头顺序改由设置决定，14 个表头里生效的 7 个按序取） |
| 补位空格子 | 保留，但 key 要**补零**（`useTaskCalendar.ts:56-68` 现在是 `` `${y}-${m}-${d}` ``，与按日期拼 key 的其他地方不一致）；**补位格可聚焦但不可操作**，与真实日区分（APG 的"方向键落在无效格上应跳过"的思路，[07](07-调研附录.md) §3.5） |
| 每格纵向堆叠文本行 | **改造**（见 §3.2） |
| 颜色只按 `window_type` | **改造**（见 §5） |
| — | **新增**：跨日条、密度折叠、点击进详情 |

**周起始日要能改，而且默认值取自区域设置。** CLDR 的 `firstDay` 在 CN 是**周一**、在 US/JP/KR/TW 是**周日**（[07](07-调研附录.md) §3.3），而现状两处都写死周日起始：`TaskCalendar.tsx:88-94`（7 个全写表头）与 `:95-101`（7 个简写表头）都是「周日 周一 … 周六」字面量，`useTaskCalendar.ts:44-47` 用 `new Date(y, m, 1).getDay()`（0 = 周日）推网格偏移。对中文用户这是错的。

**但只按 locale 推导还不够。** Google 日历把这件事做成了**用户设置项**（`设置 → 视图选项 → 选择日历周的开始日期`，[官方文档](https://support.google.com/calendar/answer/6110849)）。理由不难想：地区习惯决定**默认值**，个人习惯决定**实际值**——同一个中文用户里，有每周一开会的，也有周日出发的。

→ 实现分两层：

1. **默认**取 `new Intl.Locale(navigator.language).getWeekInfo?.().firstDay`（1 = 周一 … 7 = 周日），取不到回落**周一**（本项目中文优先）。周末高亮同理取 `weekInfo.weekend`，缺省 sat/sun。
2. **设置项**存用户显式选择（复用项目的用户设置存储，`/settings` 或 `/color` 那类页面加一项）。设置优先于 locale。**URL 参数 `?week=mon` 用于深链接与测试**，优先级最高。

14 个表头要改成数据驱动——维护两个 7 元素的中文字面量数组（全写 `周日…` 与简写 `日一二…`），按 `firstDay` 偏移取值后取 7 个渲染；`useTaskCalendar.ts:47` 的 `startDow` 同步改成同一口径。

### 3.2 每格的展示

紧凑档（默认，折叠到 3 条）：

```
┌──────────────────┐
│  3        ●2     │ ← ① 日期数字（左） ② 建议数徽标（右）
├──────────────────┤
│▓09:00 站会        │ ← ③ 事件条（带时间前缀）
│▓11:00 写周报 ▪    │   ▪ = p1 优先级角标（右上角小方块）
│▓14:00 - - - - -  │ ← ④ 建议条：虚线边框 + 淡底（§5.3）
├──────────────────┤
│  +2 更多          │ ← ⑤ 折叠行（**位置常驻**，不 hover 才出现）
└──────────────────┘
```

五个部件逐条说明：

| # | 部件 | 规则 |
|---|---|---|
| ① | 日期数字 | `--t-text-sm`；今天加 `--t-color-accent` 加粗；非本月补位格降为 `--t-color-ink-faint` |
| ② | 建议数徽标 | `●N`（N = 该天建议数）。**仅在 N>0 时渲染**，且必须**预留位置**（宽度固定），否则建议从 0 变 1 时整行重排 |
| ③ | 事件条 | 见下面的条形规格 |
| ④ | 建议条 | 虚线边框 + 4% accent 底，**必须比真实事件淡**（§5.3 的 P9 边界） |
| ⑤ | 折叠行 | 恒占一行高度，内容为 `+N 更多`。**这是 APG 占位要求的直接应用**——不 hover 才出现，否则鼠标划过时整格重排 |

**事件条的规格**（从"整行文字"改成"带时间前缀的条"）：

```
标准档（折叠 5 条）      紧凑档（折叠 3 条，默认）
┌──────────────────┐   ┌──────────────────┐
│▓09:00 站会         │   │▓09:00 站会        │
│▓10:00 一对一 ▪     │   │▓11:00 写周报 ▪    │
│▓11:00 写周报       │   │▓14:00 - - - - -  │
│▓14:00 需求评审     │   │  +3 更多          │
│▓16:00 - - - - -   │   └──────────────────┘
│▓17:00 复盘         │
│  +2 更多          │
└──────────────────┘
```

事件条**行高固定 20px**（不参与密度档，密度只控制条数——MD3 的理由见下）。超长标题单行省略号。

**为什么折叠**：每格纵向堆叠超过 4 行，格子高度撑爆或者文字被 CSS 裁掉。折叠成 `+N 更多` 是经典做法（Google 日历的月视图更激进，只显示点阵）。点 `+N` 弹出当日列表。

**为什么折叠到 3 条**：每格纵向堆叠超过 4 行，格子高度撑爆或者文字被 CSS 裁掉。折叠成 `+N 更多` 是经典做法（Google 日历的月视图更激进，只显示点阵）。点 `+N` 弹出当日列表。

**密度应该是一个设置项，不写死。** Google 日历把它做成**三档用户设置**：自适应（按大屏动态缩放放大活动）/ 标准 / 紧凑（[官方文档](https://support.google.com/calendar/answer/15619910)）。本设计的"折叠到 3 条"其实是"紧凑档"，所以应该做成**两档设置**：标准档折叠到 5 条、紧凑档折叠到 3 条，默认取紧凑（本月网格格子本身就窄）。

**但密度只控制"显示几条"，不控制"每条多高"。** MD3 官方无障碍规范把这条界线画得很清楚（[原文](https://m3.material.io/components/date-pickers/accessibility)）：

> "Interactive targets for all elements meet Material's 48x48dp minimum touch target requirement. **Increasing density would negatively impact accessibility by limiting tappable/clickable targets.**"

→ 读法：**折叠是安全的（少显示几条），压缩是不安全的（让每条更矮更密）**。所以事件块高度不参与密度档，守 §4.2 的 24px 下限；密度只管月网格里的条数。

**顺带说「自适应」那档**：Google 的描述是"日历会根据大屏幕显示器动态缩放并放大活动"。这正是本项目 `@container` 查询已经做的事（`AGENTS.md` 记着"容器查询用于组件级自适应"）——所以宽屏下的"放大活动"可以直接靠容器查询实现，不必另设一档。

**事件条的位置必须预留，不许 hover 才出现。** WAI-ARIA APG 的 Date Picker 模式有一条明确要求：焦点环与 hover **共用同一套边框样式并预留 padding 占位**，避免状态出现时布局跳动（[07](07-调研附录.md) §3.4）。这里的道理一样——如果某个操作按钮是 hover 才浮现的，鼠标划过时整格的文字会重排，用户正准备点的那个位置就跑了。宁可让那一行一直空着。

**无时间窗口的任务不进日历。** 现状是 `INNER JOIN time_window`（`task/repository/query.rs:268-381`），这是对的——日历是"有时间的安排"，没排期的任务属于列表。但**逾期未排期的任务**需要被看见，方式见 §3.4。

### 3.3 跨日事件

现状只落在 `ev.start` 那天（`useTaskCalendar.ts:56-68`）。改造为**真正的跨日条**：

```
┌───────────────────────────┐
│ 2  ┃████████████          │  ← 从 2 日延续过来的条（左侧断口）
│ 3  ┃██████████████        │
│ 4  ┃████████████          │  ← 到 4 日结束（右侧断口）
└───────────────────────────┘
```

实现上不需要后端改：**`CalendarEvent` 已经带 `start` 与 `end`**，前端按日切分渲染即可。切分逻辑要处理 `end` 恰好落在午夜的情况——用**半开区间 `[start, end)`** 约定（与项目 `time_window` 的 `start_time < end_time` CHECK 及 C002 的重叠判据 `sa < eb && sb < ea` 一致，[04](04-数据模型.md) §2.2 也沿用了这个约定）。

`end` 恰好等于午夜 → 那天**不画**（属于次日）。这与 C002 的"边界相接不算重叠"是同一个约定，全项目统一。

### 3.4 逾期标记

日历是"我承诺的安排"，不是"我欠的债"。所以**逾期任务不在月网格里单独铺一层**——那会让整张日历变红。

处置：**日期数字本身**承载逾期信息。

```
┌────────────────┐
│ 3  ⚠           │  ← 今天，⚠ 表示这天有逾期未完成
│ 4  ●2          │  ← 这天有 2 条建议
└────────────────┘
```

`⚠` 用 `--t-color-accent`（信号色，目录绿）。点击日期 → 切到日视图，日视图里列出"这天逾期的任务"清单。

**为什么逾期不用红色。** WCAG 1.4.1 Use of Color 规定颜色**不得是唯一的编码**，其失败准则 F81 明确把"仅用颜色表达必填/错误状态"判为失败（[07](07-调研附录.md) §3.7）。本项目**有** `--t-color-danger`（`oklch(55% 0.16 25deg)`），拿它标逾期是顺手的事，但只要它成了逾期的唯一标识就踩了 1.4.1。图标 + 数字是形状与文字，不受该准则约束，所以 `⚠` 是正解。**注意这条也约束 §5 的事件块**：优先级若用颜色区分而没有角标，同样不合规。

## 4. 周/日时间轴

### 4.1 结构

日视图（单列，刻度列宽 56px）：

```
       09:00  10:00  11:00  12:00  13:00  14:00  15:00  16:00
       ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┐
       │      │      │      │      │      │      │      │  00:00
  ⋮    │      │      │      │      │      │      │      │
       │      │      │      │      │      │      │      │  01:00
  ⋮    │      │ ┌────────────┐ │      │      │      │
       │      │ │ 写周报  p1 │ │      │ ┌──────────┐  │
       │      │ └────────────┘ │      │ │ 需求评审  │  │  03:00
  ⋮    │      │      │      │      │ └──────────┘  │
       ├──────┼──────┼──────┼──────┼──────┼──────┼──────┤ ← 整点线（1px）
       │ ┌──┐ │      │      │      │      │      │      │
  14:20│ │事│ │      │      │      │      │      │      │ ← 当前时间线
       │ └──┘ │      │      │      │      │      │      │
       └──────┴──────┴──────┴──────┴──────┴──────┴──────┘  18:00
```

周视图（7 列）**结构完全相同**，只是横向铺 7 列，列头是 `周一 … 周日`（顺序由 §3.1 的设置决定）。

逐部件：

| 部件 | 规格 |
|---|---|
| **左侧时间刻度列** | 宽 56px（窄屏 40px），`--t-font-mono` + `tabular-nums`，**只标整点**（`09:00`），不标 15/30/45——否则刻度列会宽到吃掉正文 |
| **全天行（all-day row）** | 网格顶部独立一条，高 24px（单行）+ 可滚动。只放跨日事件；`feasible` 在这里也**不画**（§5.2），只显示存在性徽标 |
| **当前时间线** | 1px `--t-color-accent` 横贯整幅网格 + 左侧刻度列上的 `14:20` 标签。每分钟更新（`setInterval`，组件卸载时清） |
| **整点分隔线** | 1px `--t-color-border` 横贯 |
| **刻度线** | 仅 `:45` 一档，`--t-color-ink-faint` 20% 透明；`:15`/`:30` **不画**（密度太密反而读不出刻度） |
| **工作时段外** | 默认 09:00 前 / 18:00 后用 `--t-color-bg` 底，刻度降为 `--t-color-ink-faint` |

**默认滚动位置**：滚到当前时刻（或工作时段起点，取较早者），而不是 `00:00`。理由：让用户一进来就看到"现在"——这是时间轴视图的全部意义。

**工作时段外**（默认 09:00 前、18:00 后）用 `--t-color-bg` 底或降低刻度对比度，视觉上退后。

### 4.2 事件块的呈现

四个高度档，**结构固定，只是内容随高度增减**：

```
24–44px（≤30 分钟）        44–72px（30–90 分钟）
┌────────────────┐         ┌────────────────┐
│ 写周报      ▪  │         │ 写周报      ▪  │
└────────────────┘         │ 这周先把框架   │
                            │ 搭出来         │
                            └────────────────┘
> 72px（>90 分钟）
┌────────────────────────────┐
│ 写周报               ▪     │
│ 14:00–16:00                │
└────────────────────────────┘
> 120px（>4 小时，或跨工作时段）
┌────────────────────────────┐
│ 深度评审会             ▪    │
│ 14:00–17:30                │
│ 上周遗留的方案还没定稿     │  ← description 首行
└────────────────────────────┘
```

| 档 | 条件 | 显示 |
|---|---|---|
| 1 | **< 44px** | 标题（单行，省略号）+ 优先级角标 |
| 2 | 44–72px | 标题（可两行）+ 优先级角标 |
| 3 | > 72px | 标题 + **时间范围** |
| 4 | > 120px | 标题 + 时间范围 + **description 首行**（仅已排期的有描述） |

**高度 ∝ 时长**，换算：`高度 = (end − start) × 每分钟像素`，**最短 24px**，最长撑满（超出 24 小时的部分截断）。

**优先级角标**（`▪`）是一枚 6×6px 的小方块，**右上角**，`--t-color-accent`：

| 优先级 | 角标 | 备注 |
|---|---|---|
| p1 | 实心方块 | |
| p2 | 50% 透明方块 | |
| p3 / p4 | **不显示** | 避免整屏都是方块 |

**为什么角标是形状而不是颜色**：WCAG 1.4.1 禁止颜色是唯一编码（§5.2）。"实心 / 半透明 / 不显示"这个三级梯度即使全灰也能分辨。

**为什么最短是 24px 而不是更小。** WCAG 2.5.8 Target Size (Minimum) 要求 24×24 CSS px（AA 级）；它的"用户代理默认值例外"只覆盖**日历月视图的日期格**，而事件块是日期格里的**另一个**可操作对象，不在例外内（[07](07-调研附录.md) §3.2）。同一份规范的参照值：iOS/iPadOS 默认 44pt / 最小 28pt，macOS 28pt，Android/MD3 ≥48dp。**24px 是这套数值里最低的一档，所以事件块取它，日期格可以更小。**

**信息 scent**：这个"高度 → 显示什么"的规则来自 Nielsen 的 information scent（与 P3 引用的同一条判据）——用户扫一眼就知道"点进去有什么"，不必点开。

### 4.3 重叠布局

**这就是区间图着色（interval graph coloring）**：把互相重叠的事件分到最少的列里。答案是图的最大团 = **最大同时重叠数**，而**按左端点排序的贪心即达到这个最优，且是线性时间**（CLRS 第 16 节 / p.379；[07](07-调研附录.md) §3.6）。

```
09:00 ┌───┐┌───┐
      │ A ││ B │
10:00 │   ││   │
      │   │└───┘
11:00 └───┘
```

实现（纯计算 + CSS，不引第三方库）：

```
1. 取当天全部事件，按 start 升序（并列时按 end 升序）
2. 每列记住它最后一个事件的 end
3. 依次为 ev 找**第一个** end <= ev.start 的列，放进去；没有就新开一列
4. 列数 == 最大同时重叠数（贪心即最优，无需回溯）
5. 宽度：整幅时间轴按当天**实际用到的列数**等分，每个事件占一列，
   减 1px 间隙；高度 = (end - start) 映射到像素
```

第 3 步用的是**半开区间**（`end <= start` 即可复用该列），与 C002 的重叠判据 `sa < eb && sb < ea` 以及 [04](04-数据模型.md) §2.2 统一——边界相接不算重叠，全项目一个约定。

**这一步消掉了上一版文档里的技术债。** 上一版先分 cluster、再处理"事件 A 跨了两个 cluster 要在两处都画一遍"——那个 cluster 中间结构是多余的：既然每个事件从头到尾只属于一列，就不存在"跨 cluster"的情况。**所以 [06](06-日历视图.md) §7 的技术债表里不再有"精确的 interval-graph 布局"这一条。**

"同簇等宽展开" vs "左对齐固定宽留白"（Google 日历展开、Outlook 有时留白）是算法之外的**呈现选择**，本设计选**展开到 100%**：当天只有两个事件时它们各占半宽，而不是挤在左半边。

### 4.4 跨日事件在时间轴上

跨日的 `planned`/`actual` 事件在时间轴上**只画起始日那一份**，但那个块的左边缘加一条"延续"标记（一条 2px 的竖线 + 左侧箭头），hover 时 tooltip 显示"延续至 X 日"。

不做真正的跨日横向拉条——那需要在整个网格上做 clip，复杂度高而周视图里跨日事件本就罕见（跨日的通常是 `feasible` 声明，而 `feasible` 在时间轴上**不画**，见 §5.2）。

## 5. 颜色与状态语义

### 5.1 现状的问题

`TaskCalendar.tsx:9-17` 按 `window_type` 分三个 CSS 类（feasible/planned/actual，未识别回落 planned），而 `CalendarEvent.status` **完全未被使用**。结果是：一件已完成的任务和一个待办的任务在日历上长得一样。

### 5.2 新的语义

三层语义用**三个正交通道**表达：

| 通道 | 承载什么 | 手段 |
|---|---|---|
| **边框样式** | 时间窗类型 | `planned` 实线 / `actual` 实线加粗 / `feasible` 虚线 |
| **色块底色** | 任务状态 | `active` → `--t-color-accent` 6% / `backlog` → `--t-color-surface-raised` / `completed` → 无底色 + 标题删除线 |
| **角标** | 优先级 | `p1` 一个小方块（`--t-color-accent` 实心）/ `p2` 半透明 / `p3` `p4` 不显示 |

**这个三通道设计的依据是无障碍规范，不是审美偏好。** WCAG 1.4.1 Use of Color 允许颜色编码信息，但**禁止颜色是唯一编码**（[07](07-调研附录.md) §3.7）。三通道里：

- **边框样式**是形状（实线/虚线/加粗），不依赖色觉；
- **角标**是形状 + 位置 + 可选的填充度差异，不依赖色觉；
- **底色**是唯一真正用颜色的通道，它承载的是 `status`——而 `status` 另有冗余：**`completed` 带删除线**。

所以任一语义都至少有一个非颜色通道。这也意味着：**如果哪天有人想"简化"成只靠底色区分状态，那是让代码更短但让日历不可用**，这不是风格问题。优先级角标的实心/半透明/不显示是三级梯度，即使全部无色也能靠"有没有方块"和"方块有多实"分辨。

**`feasible` 在时间轴上不画。** 理由：它是"我大概有空"这种**元信息**，画进时间轴会让人误以为那是安排。而 `planned` 是"我要做"、`actual` 是"我做了"，都是安排。`feasible` 只在**任务详情页**与**月网格的鼠标悬浮**里可见。

这是一个真实的取舍——`feasible` 是用户手工建的（`TimeWindowsTab.tsx` 的"今天 9-11"之类预设），直接不显示会让用户困惑。对策：**月网格里当天有任何 `feasible` 时，日期数字旁显示一个极小的空心方块**，hover 显示"这天你标记过可做时段"。存在性可见，具体不占版面。

### 5.3 建议块的呈现

建议（[05](05-排序与推荐.md) §3）**不落库**，所以它是**纯前端的虚拟层**。三种置信度的对照：

```
high（明确 due + 用户给的时长）    medium（时长被截断 / due > 7 天）
┌ - - - - - - - - - ┐            ┌ - - - - - - - - - ┐
┆ 写周报         ▢  ┆            ┆ 整理照片       ▢  ┆
┆ 今天到期 · p1    ┆            ┆ 时长已按上限截断 ┆
└ - - - - - - - - - ┘            └ - - - - - - - - - ┘

low（时长是估的）
┌ · · · · · · · · · ┐
┊ 读那本书      ▢  ┊    ← 点线边框 + 标题前缀「约」
┊ 约 16:00 · 时长是估的┊
┘ · · · · · · · · · ┘
```

| 元素 | 表现 |
|---|---|
| 边框 | **1px 虚线**，`--t-color-accent` 40%；`low` 改**点线**。与 `feasible` 的虚线靠**色相**区分（`feasible` 灰调、建议绿调） |
| 背景 | `--t-color-accent` **4%**（不是 `opacity` —— `opacity` 会让文字一起变淡，forced-colors 下直接丢失，见 P12） |
| 标题 | 与事件块同字号，`--t-color-ink-muted`（**比真实事件淡**——它还不是承诺） |
| 理由行 | `--text-2xs`，`--t-color-ink-faint`。**只放最高贡献的那一条**，完整分解在 tooltip |
| 右上角 `▢` | 采纳按钮。**位置常驻**（不 hover 才出现，理由同 §3.2 部件⑤） |
| `confidence: low` | 边框点线 + 标题前缀「约」+ 理由行显式写"时长是估的" |
| 整块点击 | 打开任务详情（与事件块一致，**不跳走**） |

**建议必须比真实事件更淡。** 这是 P9 在视觉上的落点：如果建议长得和真实安排一样，用户就无法区分"这是我的计划"和"这是系统的猜测"，而那个区分是本设计最重要的那条边界。对照 **Things 3 把日历集成默认关闭**的做法（[07](07-调研附录.md) §3.12）——那条教训是"用户未必想看系统的猜测"，所以建议图层**必须能一键关掉**。

**图层开关**：时间轴右上角一个 `建议 ☑` 复选框，默认**开**。用户可以关掉它专注执行。这是 P9 的第二层保险——不采纳也是一种操作。

## 6. 交互

### 6.1 拖拽落位

从任务列表把任务拖到时间轴 → 在落点创建 `planned` 窗口。这是 [03](03-录入模型.md) §6 里"后添加属性"的一条路径，也是**用户最自然的排期动作**。

#### 头号反例：Things 3 故意**不**这么做

Things 官方支持文档的原话（[Getting Productive with Things](https://culturedcode.com/things/support/articles/6378414)）：

> "**Your calendar complements Things: it's where all of your appointments and events belong.** Plan smart by seeing Calendar entries **at a glance alongside** your to-dos in Today and Upcoming. **You can turn the feature on** in Things' Settings."

也就是说，Things 的日历是**只读叠加的预约视图**，用户**不能**把任务拖到日历上，而且这个功能**默认关闭**。而它的排程模型是**列表**（Today / Upcoming / Anytime / Someday），不是时间轴。一个拿了 Apple Design Award、卖了近十年的产品选了完全另一条路。

**为什么这不推翻本设计，但必须回应**：

| | Things | 本设计 |
|---|---|---|
| 排程的载体 | **列表**：任务属于哪个列表 | **时间轴**：任务落在哪个时段 |
| 日历的角色 | 只读展示外部预约 | 任务自身的执行时段也画在上面 |
| 时间精度 | 天（官方明确说 start date **不是**时长） | 15 分钟 |

差别在**排程的载体**这一条。Things 的 `start date` 是"我想在哪天开始做"（天粒度），它不需要小时级的时段；本设计要做的是"这两小时做这件事"，那载体就只能是时间轴。**载体不同，"往哪拖"这个问题才存在。**

**但 Things 给了一条必须吸收的警告**：日历视图**默认关闭**比默认打开更符合用户预期。所以 [06](06-日历视图.md) §1 的"默认落在哪个视图"值得重新掂量——Things 的答案是"默认列表，日历是可选的增强"。本设计仍选周视图为默认（排期是主线），但**"显示/隐藏日历面板"要是一个能在工具条上直接切的东西**，而不是要先切视图模式。

顺带采纳：Things 的日历集成是**叠加**（在 Today/Upcoming 列表里看一眼预约），不是**跳转**。所以点时间轴上的事件开详情抽屉（[06](06-日历视图.md) §6.3）是对的——不跳走，日历还在视野里。

**反馈契约逐条照 Apple HIG Drag and drop**（出处见 [07](07-调研附录.md) §3.5）：

```
指针移动：
  移动不足 3pt —— 什么都不发生（还在点选，不是拖拽）
  移动超过 3pt —— 出现半透明拖影，内容是任务标题

拖拽中：
  半透明拖影跟随指针（用户能看见拖影下面是什么）
  幽灵块实时吸附到 15 分钟网格（默认时长 60 分钟或已有 effort）
  悬停在**合法**落点上方时，该时段高亮
  移开合法落点 —— 高亮立刻消失
  悬停在**非法**落点（桶内已有安排）上方 —— **不给高亮**

放下：
  1. POST /api/tasks/{task_id}/blocks  { kind: "planned", start_at, end_at }
  2. 乐观更新：本地插入，失败回滚 + toast
  3. C001 不通过（不在任何 feasible 段内）—— 不弹确认框，落位成功，
     toast 里给「撤销」（[05](05-排序与推荐.md) §3.5 方案 C 的变体）
```

三条 HIG 规则背后是同一个判断，值得说清：

- **"非法目标不高亮"**——先高亮再拒收，用户会认为是 bug。这是 HIG 明确禁止的模式。
- **"优先撤销而非确认"**——HIG 直接说 drag 的错误处理应当用 undo 而不是 confirm 框。落位是**可逆**操作（删掉窗口即可），可逆的操作不该用模态框打断节奏；一天排十几个时段的话，每个都弹一次确认框会把这功能废掉。
- **"3pt 阈值"**——不加阈值的话，事件块上的**点击**（打开详情）会被判成拖拽起点。HIG 原文是 "as soon as people drag a selection **about three points**"，给的是**距离**不是时间，别自己发明一个 200ms 之类的数值。

**拖拽移动已有事件**同理，`PATCH /api/tasks/blocks/{id}` 改 `start_at`/`end_at`。注意 `src/modules/task/block.rs` 的 `TaskBlockService` —— 改了时间会触发 C001/C002 校验（[01](01-现状与问题.md) §3 的历史记录）。拖拽总是改时间，所以校验正常触发。

**C002（桶内重叠）**会让 `POST` 返回 409 + `RESOURCE_IN_USE`。前端要把它渲染成"这段时间已经有一件事了"——**在放下之前就该知道**（因为不合法的地方不给高亮），所以这个错误只可能来自"拖拽过程中状态变了"（比如两个窗口同时落位）。这时同样走撤销，不走弹窗。

### 6.2 拖拽时长

事件块**底边**可拖拽改时长。`min` 15 分钟，吸附 15 分钟网格。

对应 C001：拖长之后若超出了 `feasible` 段，**当场**就该有反馈——在拖拽过程中把超出 `feasible` 的部分画成斜纹（`repeating-linear-gradient`），松手前就知道会失败。这比"松手后弹错误"好得多（**P12 允许 `repeating-linear-gradient`，它不是阴影不是渐变装饰，是斜纹填充语义**；注意项目禁 `!important`、禁投影渐变，斜纹用 `repeating-linear-gradient` 是安全的，但要用 `@media (forced-colors)` 与 `prefers-contrast` 降级）。

### 6.3 点击与键盘

现状"点事件无反应"是明确缺口。新的交互契约：

| 操作 | 结果 |
|---|---|
| 点事件 | 打开任务详情（右侧抽屉，不是模态——模态会盖住日历，失去参照） |
| 悬停事件 | tooltip：标题、状态、时间范围、时长估算、依赖提示 |
| 点日期格（周视图） | 聚焦那天的日视图 |
| 点空白时段 | 打开"新建任务"抽屉，预填该时段为 `planned`（**先建任务还是先建窗口？** 见下） |
| 键盘 | 事件块可 `Tab` 聚焦、`Enter` 打开详情、`Delete` 删除窗口、`↑↓` 在事件间移动 |

**点空白新建的语义**：先弹任务详情抽屉（标题空、时段已预填），提交时**一次性**创建任务 + `planned` 窗口。这需要一个新的组合端点，否则要两次请求且可能只成功一半：

```rust
// POST /api/tasks
pub struct CreateTaskRequest {
    // 已有字段
    // 新增：可选的初始时间窗（一次请求建任务 + 窗口，事务内）
    #[serde(default)] pub planned_window: Option<PlannedWindowInput>,
}

pub struct PlannedWindowInput { pub start: DateTime<Utc>, pub end: DateTime<Utc> }
```

**这是本设计唯一一处"创建即带窗口"**。它不走建议、不违反 P9（用户自己点的），且避免了半成功状态。

### 6.4 键盘可达性

a11y 硬要求。规范出处见 [07](07-调研附录.md) §3.2 / §3.4 / §3.5 / §3.7。

**先做一个取舍：日历浏览靠"单字母键"还是"方向键网格"？**

两种模型都成立，参照物不同：

| | **全局单字母键** | **方向键网格** |
|---|---|---|
| 参照 | Google 日历：`j`/`n` 下一段、`t` 今天、`g` 跳指定日期、`/` 搜索、`s` 设置、`+` 添加、`?` 列出全部 | WAI-ARIA APG Date Picker Dialog：`←→` 前后一天、`↑↓` 同星期几跨周、`PageUp·Down` 换月 |
| 优点 | 不用把手从鼠标挪到"日期格"上；跳到任意日期只要 `g` | 与读屏的 grid 心智模型一致；不需要记键位 |
| 缺点 | 与输入框冲突（必须判断焦点不在 input 里）；`j` 在中文输入法里是拼音首字母 | 浏览长距离移动很慢（跨月要按 30 次） |

**APG 那套本来是给"日期选择器"设计的，不是给"日历浏览"设计的。** 日期选择器是弹窗里选一个日子，选项有限；日历浏览是要在长时间轴上快速位移。两者的导航需求不同。

→ **本设计两者都要，分工明确**：

- **单字母键管"位移"**（浏览层）：`j`/`k` 下一段/上一段、`t` 回到今天、`g` 跳到指定日期、`?` 列出全部快捷键。**`g` 是这套的关键**——没有它，方向键跨月要按 30 次。
- **方向键管"焦点"**（选择层）：在选中某个事件块之后，`←→` 改时间、`↑↓` 在事件间移动。

**单字母键必须避开输入焦点**，判据是 `document.activeElement` 不是 `input`/`textarea`/`[contenteditable]`。而且这些键**默认可以关掉**——Google 就是把它放在设置里的复选框（默认关闭），因为全局劫持字母键对中文输入法尤其危险。

**网格结构（WAI-ARIA APG Grid 模式）**

- 时间轴与月网格都是 `role="grid"`，事件块是 `role="button"` 的 `<button>`。
- **整个网格只有一个 Tab 停靠点**，格内用 **roving tabindex** 移动焦点。不是 42 个格子按 42 次 Tab。
- **每个格子要么含可聚焦元素，要么自身可聚焦**——月网格的空白格也要能落焦点。
- **焦点态与选中态必须视觉可区分**（APG 明确要求）。二者都要在 `@media (forced-colors)` 下可见。

**格内键位（APG 的约定，其中 `Home/End` 按 MD3）**

| 键 | 行为 |
|---|---|
| `←/→` | 前后一天。**周视图里跨到下周时保持同一星期几**（APG 对 layout grid 的换行要求） |
| `↑/↓` | **同一天的前/后一周**（保持星期几不变）——不是"上一行/下一行" |
| `PageUp/PageDown` | 上/下月的**同一天** |
| `Shift+PageUp/PageDown` | 下/上一年的**同一天** |
| `Home/End` | **本月的第一天 / 最后一天**（← 照 MD3，不照 APG，理由见 [07](07-调研附录.md) §3.4） |
| `Enter` | 打开详情；在日期控件里则确认并关闭 |
| `Esc` | 关闭浮层并**把焦点还给打开前的元素**（与项目命令面板同一做法） |

`PageUp/PageDown` 与 `Shift+PageUp/PageDown` 都保持"同一天"，与 MD3 一致（"Move to the same date on next/previous month"）。**方向键的日导航只有 APG 有规定**——MD3 官方键位表里根本没列，所以方向键按 APG 走。

**两条 MD3 明确的补充**：

- **星期表头不可聚焦**。MD3："Days of the week are not interactive and are therefore **not focusable via keyboard**"。所以 `↑/↓` 不会停在"周一"表头上，roving tabindex 的循环只在日期格之间。
- **日期格的 `aria-label` 必须是完整日期**。MD3："labels are used to enumerate the complete date... to hear **'Monday, August 17'** instead of just part of the date"。所以 `aria-label` 不能只有 `17`，否则读屏用户听不出是哪天。
- **日期文字对比度 ≥4.5:1**（MD3）。这条进 P12 的验收：`--t-color-ink-muted` 落在日期数字上时要验一下，不是所有主题下都自动达标。

月份/年份标题是 `aria-live` 区域，翻月时读屏要念出来。

**拖拽的等价路径（WCAG 2.5.7，AA 级硬要求）**

WCAG 2.5.7 明确点名了两种替代形态：滑块旁的文本输入框，或**列表项旁的可点击上下移动按钮**。本设计两者都要：

1. 事件块聚焦后 `Enter` → 弹"改时间"面板（数字输入）——精确调整。
2. 事件块聚焦后 `↑/↓` + `Alt`（或直接两个小按钮）= **上移/下移一个 15 分钟格**——高频操作用它。

**没有等价路径的拖拽是 WCAG 2.5.7 的失败**，不只是"体验差一点"。

**其他**

- 触摸目标 ≥24×24 CSS px（事件块，见 §4.2；日期格可用 UA 默认值例外）。
- 颜色不是唯一信息通道（WCAG 1.4.1，见 §5.2）。
- 长按弹出的菜单必须**可中止**（WCAG 2.5.2 Pointer Cancellation）。
- **动画要有开关**。Google 把「开启/关闭动画」列在认知辅助功能里（[官方文档](https://support.google.com/calendar/answer/16271522)）——日历是长列表，动画多了会真的妨碍阅读。本项目的 `--t-transition-*` 动效很短，但日历的时间线与建议块出现动画应该受 `prefers-reduced-motion` 控制，且提供显式开关。
- 焦点环用 `--t-ring-accent`（`tokens.css:47`，`0 0 0 3px` 的 accent 环）——**注意项目里没有 `--ring-float` 这个令牌**，那是被误引的 swiss 文档里的东西，别照着写。

## 7. 本期不做（技术债，明确记录）

| 不做 | 理由 | 影响 |
|---|---|---|
| ~~精确的 interval-graph 重叠布局~~ | **已做掉**——§4.3 的贪心本就是最优且线性，原先的 cluster 技术债不存在了 | 无 |
| 真正的跨日横向拉条 | 需要整网格 clip | 跨日事件在时间轴上只画起始日 |
| 时间轴上的 `feasible` 可视化 | 语义上它不是安排（§5.2） | 用户需要点进详情才看到自己标记的可做时段 |
| 日历事件与外部日历源（ICS 导入导出） | 与本轮目标无关 | 建议算法读不到外部安排，`busy` 只有内部数据 |
| 时区切换 | `WorkingHours` 本身就存本地钟点（[05](05-排序与推荐.md) §6） | 跨时区用户偏移 |
| 农历 / 闰月 | 本项目不做中式历法；CLDR 只管公历与 `firstDay` | 中文用户看公历 |

最后一条要特别说明：**建议算法的 `busy` 集合只含本系统的 `planned`/`actual`**。如果用户把真实世界的会议放在别的日历软件里，系统完全看不见，会建议出"开会的时间"。缓解：界面上明确写"基于你已安排的时段"（而不是"基于你的日历"），不承诺它知道用户全部的安排。**不要在文案里说"你的空闲时间"**——那会是一个不兑现的承诺。

**这条文案现在有了依据，不只是谦虚。** Kocielnik, Amershi & Bennett（CHI 2019）证实**事先校准期望**能显著提高用户对不完美系统的接受度（[07](07-调研附录.md) §3.9）——而"说清边界"正是校准。同一研究还表明**误报的代价高于漏报**，所以在 ICS 导入缺席的情况下，宁可少建议也不要建议出一个假的空闲。
