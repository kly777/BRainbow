## 1. 录入侧：已验证有效的做法

### 1.1 GTD 的 capture 阶段

1. **Inbox 不需要成型，只需要"让你回看时能想起当时的意图"。** OmniFocus 官方 GTD 白皮书（David Allen 背书）："It doesn't need to be fully developed; it just needs to make enough sense that when you return to the Inbox, you can recall your intention for the entry." **[官方]**
   → 落地：[03](03-录入模型.md) §4 的收件箱语义。
2. **收件箱不是待办列表，澄清过的条目不许回流。** Allen《Getting Things Done》(2001) p.27："Do not use one's inbox as a 'to do' list. Do not put clarified items back into the inbox."（转引自 Wikipedia GTD 条目）**[官方]**
   → 落地：[05](05-排序与推荐.md) §2.2 的次级键用 `created_at ASC`（先进先出）。
3. **逐条澄清，且澄清是独立于录入的仪式性活动。** Wikipedia 条目引 p.122："each item is clarified and organized by asking and answering questions about **each item in turn**"；Omni 白皮书的 Process 定义："Take a look at all your captured ideas **one at a time**..." **[官方]**
   → 这是 P8 的直接依据：**"决定先做哪件"是一个独立活动，值得系统承担。**
4. **收件箱要能接住"想做的事"。** Cultured Code 官方指南："**If you only add your obligations, looking over your to-dos will become a chore.**" **[官方]**
   → 落地：[03](03-录入模型.md) §4 的列表里"想做：整理照片"与"该做"混在同一收件箱。
5. **收件箱必须配一个"每天/每周看一遍"的仪式。** Cultured Code："Taking a second look at all of the new to-dos in your Inbox **daily** is an easy yet powerful habit."；GTD 侧对应 weekly review（Wikipedia 引 p.50、p.215–219）**[官方]**
   → 本期不做 weekly review 仪式，但列表默认视图的"收件箱"分组是它的载体。

### 1.2 快速录入

6. **回车即创建、焦点留在输入框，是连续录入的前提。** Todoist / TickTick 官方帮助都是这个模式；Cultured Code 的表述是"The faster you can get new to-dos into your Inbox, the faster you can get back to work" **[官方]**
   → 落地：[03](03-录入模型.md) §2.5 的交互契约。
7. **描述字段默认隐藏，按 `+` 或 `↓` 展开。** Todoist 官方："As you start typing, task actions will begin to show."；描述需按 `+`/`↓` 才出现，另有 `Show description` 设置让它常驻 **[官方]**
   → 落地：第 2 层由 `[+]` 唤出。
8. **进阶字段要可配置（显示/隐藏/排序），因为"哪些字段常用"是个人差异。** Todoist Customize Quick Add：action 可显示/隐藏/拖拽排序，移动端有 `Show All`/`Hide All` **[官方]**
   → 本期只做"两层固定结构"，不做每字段可见性配置（记为后续项）。
9. **提供"新任务的默认值"设置，把重复的分类决策前置。** TickTick Settings → General → **Task Default**，可预设新任务的 date / list / priority **[官方]**
   → 后续项。本期新建一律 `backlog` 无属性（P6）。
10. **采集通道要覆盖键盘、剪贴、服务菜单、邮件、分享扩展。** OmniFocus 3 官方手册附录 B "Capture Methods"：Clippings（Services "Send to Inbox"）、Mail Drop（邮件主题→标题、正文→note、附件→附件）、Share 扩展、纯文本按换行批量粘贴 **[官方]**
    → 本项目已有 Shift+Tab 全局浮窗 + 页面内联框（[03](03-录入模型.md) §1），本期只整合不新增通道。
11. **行内语法顺序自由，但"名称和日期优先"是惯例。** RTM 官方博客 2009-09-08："the task name and due date should always come first, but you can include the below properties in any order after that" **[官方博客]**
    → 本设计更进一步：**token 顺序完全不影响字段**（[03](03-录入模型.md) §2.3）。

### 1.3 自然语言日期解析（我们不做的部分，但坑值得记）

12. **误报是产品级常态，主流做法是"逐词撤销 + 全局关闭"两条退路。** Todoist 官方自己举例："The smart Quick Add might recognize part of your task name as a date, like 'monthly' in 'Create monthly report.' **Just click or tap the word to turn it into plain text.**" 另加一个全局 smart date recognition 开关 **[官方]**
13. **解析覆盖率天花板本身就是风险。** 同一份官方文档承认**不支持用捷克语和土耳其语写日期** **[官方]**
14. **歧义必须有明文的默认规则。** TickTick 官方："When you enter an ambiguous date in the list, the TickTick will be uniformly recognised as **the most recent valid date and time**. For example: the current actual time is 4pm, when you enter 'remind me at 9pm' it will be recognised as 9pm today." **[官方]**
15. **语法符号与误报率正相关。** 语法符号越多，越需要全局关闭与逐词撤销；RTM 上线 Smart Add 时**主动删掉了"新建后自动选中"**——因为行内语法变强之后，行内二次编辑就成了冗余 **[官方博客]**
    → 落地：P4（符号是有限资源）+ P5（本轮不做 NLP）。

16. **中文日期解析的坑是结构性的**（读 chrono-node `src/locales/zh/hans/parsers/` 源码，**[源码]**）：

| 坑 | 源码位置 | 为什么通用规则覆盖不了 |
|---|---|---|
| 凌晨 1 点前说"明天"落在**今天** | `ZHHansCasualDateParser`：`if (day1 == "明") { if (refDate.getHours() > 1) date.setDate(+1) }` | 这是产品决策，不是 bug——但用户猜不到 |
| `前`/`后`/`大前`/`大后` 相对"**明天**"而非今天（`前` = −2 天） | `ZHHansCasualDateParser` | 单独说"今天"却是 0，这套语义几乎无人猜得到 |
| "下周一" ≠ 最近的周一 | `ZHHansRelationWeekdayParser`：`上/下/这` 走 `offset ± 7 - refOffset`（严格周偏移），无前缀的"周一"走绝对值最小的 diff | **两条路径的直觉相反**，必须分开实现且都得解释 |
| "三点"要先定 12 还是 24 小时制 | `ZHHansTimeExpressionParser` 大量 `hour == 12` 分支（12am→0、12pm→12、与上午/下午/晚上/半夜组合时翻转） | 中文口语钟点没有上下午时含义模糊 |
| CJK 没有词边界 | 各 parser 的 `patternLeftBoundary()` 返回 `"()"`，注释写着 "while avoiding matching CJK characters as word boundaries" | 基于正则的解析器必须为此单独开洞 |

    → 这五条每一条都要在界面上给用户解释一遍，而解释成本高于省下的几次点击。**这是 P5 决定"不做 NLP"的主要依据。**

### 1.4 渐进披露

17. **Nielsen 的三条判据**（*Progressive Disclosure*, 2006-12-03，**[权威]**）：
    - "Initially, show users only a few of the most important options. Offer a larger set of specialized options **upon request**."
    - "**the very fact that something appears on the initial display tells users that it's important**"
    - "**designs that go beyond 2 disclosure levels typically have low usability**"
    - 每一层要有 strong information scent（让人知道点进去会看到什么）
18. **每个表单项都在消耗"解释—回忆—格式化"三重成本。** NN/g, Huei-Hsin Wang, *4 Principles to Reduce Cognitive Load in Forms*（2025-07-18，**[权威]**）："**Every field in a form demands that the user interpret the question, find the right information, and provide it in an acceptable format.**" 同文的 Progressive Disclosure 段点名 GOV.UK 的 "one thing per page" 模式，并称**单列布局在完成率上"consistently"优于多列** **[权威]**
19. **"可后加字段"的实现范式**：属性是**数据库级 schema + 按视图隐藏**，且给引擎自动字段留只读位。Notion：任意时刻加 property、`Property visibility` 按视图控制、**单库上限 500 个属性**（明说是"为了保持数据库快速可靠"）、`Created time`/`Created by` 等系统字段自动生成且不可编辑 **[官方]**
20. **属性名与类型要全局绑定，否则同一字段在不同记录里含义会漂移。** Obsidian 官方文档："Once a property type is assigned to a property name, **all properties with that name across your vault will use the same type**." 另有明确的取舍声明——"**Markdown in properties: This is an intentional limitation as properties are meant to be small, atomic bits of information**"，以及 `tag`→`tags` 之类的废弃别名（v1.4 弃用、v1.9 移除）**[官方]**
    - **"改名必然要留迁移期"是字段可后加的隐藏税**——记为后续项（若将来 `priority` 要改成别的编码方式，得考虑迁移）。

## 2. 录入侧：有争议 / 被批评的做法

| 做法 | 状态 | 反方意见 |
|---|---|---|
| **"多数任务被 defer"** | **只有断言，没有统计** | OmniFocus 白皮书原文："**Defer It**: If you can't do it right this minute, your remaining option is to defer it. (**Most of your Inbox items are probably like this.**)" ——括注是**方法论主张**。在 Todoist / Things / OmniFocus / RTM 官方文档里**都没有找到任何公开的处理结果分布数据**。任何具体百分比都应视为编造 **[官方 + 核查结论]** |
| **Todoist 用 `!1`/`!2`/`!3` 表示优先级** | **与当前官方文档矛盾** | 官方现行口径是 `p1`/`p2`/`p3`；`!` 现在表示提醒（`!14:00`、`!30 min before`）。老版本（v1 用 p1–p4）与社区文章的残留 **[官方 vs 第三方冲突]**。→ 本设计用 `!p1` 是**本项目自己的约定**，不声称兼容 Todoist |
| **AI 自动分类收件箱** | **官方已宣传，但零准确率数据** | TickTick 官方帮助的 "AI Assistant" 示例 prompt 就是 "Help me clean up my long-unfinished tasks… decide what to keep, postpone, or delete" **[官方]**，但**没有任何公开的准确率或对比数据** **[核查结论]**。且它与 GTD"capture 阶段不做任何决策"的前提**哲学冲突** **[推断]** |
| **"单一输入行"是否优于"多字段表单"** | **无共识** | Nielsen 的判据只说"高频需要的东西必须前置"，没说语法行一定赢 **[权威的边界 + 推断]** |
| **内联语法符号越多越好？** | **反向证据** | Todoist 不得不提供全局关闭 + 逐词撤销，RTM 不得不砍掉"自动选中"。语法符号与误报率正相关 **[官方 + 推断]** |
| **日期 / 开始日期 / 截止日期三字段是否必要** | **有争议** | Todoist 与 Things 都拆开（Todoist 的 `date` 与 `{march 30}` 的 deadline 是两个独立字段）**[官方]**，代价是 Quick Add 面板多两块 UI、语义更难教 **[推断]**。本设计 `start_at`/`due_at` 分列但**不给符号**（[03](03-录入模型.md) §2.1），是折中 |
| **2 分钟规则作为唯一例外出口** | **前提已变化** | Allen 原书（2001）的假设是"纸质 + 单一收件箱"；Omni 白皮书的六出口结构（Trash / Someday-Maybe / Reference / <2分钟 / Waiting / Calendar）是现代化改写 **[官方 + 推断]**，没有公开数据检验优劣 |

## 3. 日历与排程侧

> 本章上一版几乎全是 `[推断]`，且有一条无法证实的流行说法。重写后每条都有出处，
> 不能证实的单列 §3.10。

### 3.1 全天事件应独立成行

**全天事件（跨日、节假日）放在时间轴上方的独立一行，而不是塞进 24 小时网格里。** Google 日历 / iOS 日历 / Outlook 全部如此。**[观察到的产品一致行为]**

Google 的官方帮助里**没有**"为什么要这样设计"的设计文档——它只有使用说明。所以这一条**仍然没有一手设计依据**，但下面的 §3.12 补上了几条**可引用的官方事实**。

推论出一条对本项目直接有用的：**跨日事件在时间轴上只画起始日**（[06](06-日历视图.md) §4.4），因为它在网格上方有自己的行，不参与小时列的排布。

### 3.2 触摸目标与可达性

各平台与标准的实测数值 **[官方规范]**：

| 来源 | 最小目标 | 备注 |
|---|---|---|
| iOS / iPadOS HIG | **44×44 pt**（默认），28×28 pt（最小） | 44 是默认值不是下限；28 是可以接受的最小值 |
| macOS HIG | 28×28 pt | 桌面端显著低于移动端 |
| Material Design 3 / Android | **≥48 dp** | MD3 明确说这是**为日期选择器**特意放大的（见下） |
| **WCAG 2.5.8 Target Size (Minimum)** | **24×24 CSS px** | AA 级 |

**WCAG 2.5.8 有一条对本项目关键的例外**：规范明确把"日历月视图的日期格"归入 **user agent default 例外**——也就是说日期格可以小于 24px 而不算失败，前提是它是浏览器/控件库的默认行为。

→ 这不是豁免，而是**授权**：[06](06-日历视图.md) 的月网格日期格可以窄，但**日视图的事件块、周视图的日期格不是日期格**（它们承载"这一天"之外的可操作对象），仍应守 24×24。本设计原先给事件块定的最短 22px 正是踩在这条线上，**已上调到 24px**（[06](06-日历视图.md) §4.2）——这是本轮调研查出的第一处实打实的规格冲突。

**MD3 额外给了一条对"紧凑模式"的具体警告**（[官方无障碍规范](https://m3.material.io/components/date-pickers/accessibility)）：

> "Interactive targets for all elements meet Material's 48x48dp minimum touch target requirement. **Increasing density would negatively impact accessibility by limiting tappable/clickable targets.**"

→ 读法要精确：**折叠（少显示几条）是安全的，压缩（让每条更矮更密）不是**。所以 [06](06-日历视图.md) §3.2 的"紧凑档 = 折叠到 3 条"没问题，但**事件块高度不参与密度档**——事件块守 24px（见 §3.2 开头的结论），密度只控制月网格里显示几条。

### 3.3 周起始日必须取自区域设置，不能写死

**CLDR 的实际取值** **[官方规范]**：

| 地区 | `firstDay` |
|---|---|
| CN / 大部分欧洲 | **周一** |
| US / JP / KR / TW / HK / SG / TH / IN | **周日** |

短日期格式：CN 是 `y/M/d`，长格式 `y年M月d日`。周末缺省回退到 sat/sun。

→ 直接改 [06](06-日历视图.md) §3.1 的"7 列周日起始 **保留**"：**不保留**，改成按 `Intl.Locale` / 浏览器 locale 推导。现状是写死周日起始（`TaskCalendar.tsx` 的 14 个表头就是周一起序的），对中文用户是错的。

### 3.4 网格的 ARIA 语义

WAI-ARIA APG 的 Grid 模式 **[官方规范]**：

1. **整个网格只有一个 tab 停靠点**，用 roving tabindex 在格间移动焦点。不是 42 个格子 42 次 Tab。
2. **data grid 与 layout grid 的换行相反**：
   - data grid（数据表）到边界**不换行**；
   - **layout grid（如月视图 7×6）"SHOULD" 换行**。
   → 月网格的左右箭头应该跨到下一行去（同一"周"），而不是撞到边界就停。
3. **每个格子要么含一个可聚焦元素，要么自身可聚焦**。
4. **焦点态必须与选中态视觉可区分**。
5. Date Picker Dialog 的具体键位：**PageUp/PageDown = 上/下月，Shift+PageUp/PageDown = 上/下年**；上下箭头 = **同一天的上一周/下一周**（保持星期几不变）。焦点环与 hover **共用一套边框样式并预留 padding 占位**，避免焦点出现时布局跳动。月份/年份标题是 live region。

第 5 条"预留占位防跳动"对本项目有直接价值：[06](06-日历视图.md) §3.2 的月网格事件条是 hover 才出现的，必须**预留位置**，否则 hover 会让整格重排。

第 2 条"同一天跨周"是本项目当前完全没有的键位（[06](06-日历视图.md) §6.4 只写了 `↑↓` 在事件间移动），应补上：周视图里 `←/→` 跨周要落在**同一星期几**。

**MD3 的官方键位表与 APG 有出入**（[MD3 无障碍规范](https://m3.material.io/components/date-pickers/accessibility) 原文）：

| 键 | MD3 | 与 APG 的差异 |
|---|---|---|
| `Enter` | 确认；**关闭日历并保存所选日期** | APG 同义 |
| `PageUp/PageDown` | 移到**下一个/上一个月的同一天** | APG 是"换月/年"，粒度描述不同但行为相近 |
| `Home/End` | 移到**本月的第一天** | ⚠️ **本设计原写"本周首/末日"（取自 APG），与 MD3 冲突** |
| `Shift+PageUp/PageDown` | 移到**下/上一年的同一天** | APG 同义 |
| `Shift+M` / `Shift+Y` | 月 / 年下拉列表 | MD3 独有 |
| 方向键 | **未列入** | MD3 规范里根本没定义方向键的日导航 |

另外两条 MD3 明确的：

- **星期表头不可聚焦**："Days of the week are not interactive and are therefore **not focusable via keyboard**" —— 与 APG 的"每格都要可聚焦"并不矛盾，因为表头在两种模型里都是 `columnheader`，本来就不进 tab 序列。
- **读屏要念完整日期**："labels are used to enumerate the complete date... to hear **'Monday, August 17'** instead of just part of the date" —— 所以日期格的 `aria-label` 不能只有数字。

→ **取舍**：`Home/End` 照 **MD3**（本月首末日）而不是 APG，因为月网格里"跳到月初/月末"更常用，而周视图里首末日几乎等于方向键三四次的结果。同样的输入，一致的行为比"规范之间对齐"更重要。

#### 日期输入：MD3 给的三条硬规则

MD3 把"**不打开日历、直接打字**"列为**第一条**用例（[官方](https://m3.material.io/components/date-pickers/accessibility)）：

> "**Enter dates manually by inputting text, without using the picker**"
>
> "The calendar icon is the **exclusive** entry point for the date picker. This improves efficiency for a screen reader and other keyboard users, as it **makes interaction with the date picker optional** and reduces the amount of key presses required to input a date."

**这是 P5「标题行绝不解析、但日期控件内可以做」的第二个独立佐证**——MD3 的结论与 Things 完全一致：**文本输入是一等公民，日历是可选的快捷方式**。而且理由不是解析好不好，而是**按键次数**。

MD3 还给了两条很具体的实现规则，本设计照抄：

| 规则 | 原文 | 为什么重要 |
|---|---|---|
| **失焦或回车时才格式化，输入过程中不格式化** | "Automatically format the date after the user hits 'Enter' or navigates out of the text field. **Don't automatically format the date by adding slashes or other special characters while the user is typing** (also known as input masks). This can cause confusion for people using screen readers **because it changes what they typed**." | 输入掩码（`2026/10/0` → `2026/10/03`）会**改掉用户刚敲的字符**，读屏用户听到的和看到的不一致 |
| **接受多种分隔符与不补零** | "accept a range of formats including **dashes, spaces, slashes, dots**, and **0 to the left of a single digit** month/day. This is especially helpful for assistive technology users who might be more prone to errors" | 严格格式校验会把"手抖多打一个字符"变成硬错误 |

### 3.5 拖拽的反馈契约

Apple HIG Drag and drop **[官方规范]**：

- **"Display a drag image as soon as people drag a selection about three points"** —— 拖过约 3pt 就出拖影，不要等用户"明确拖起来"。
- 拖影**半透明**，让用户能看见下面的落点。
- **只在悬停于合法目标上方时高亮该目标**；拖离立刻取消高亮；**非法目标不给高亮**（给高亮又拒收是欺骗）。
- 非法放置需要**明确的失败反馈**。
- **"Offer alternative ways to accomplish drag-and-drop actions."**
- 优先用**撤销**而不是确认对话框。

**WCAG 2.5.7 Dragging Movements** 为"必须提供替代操作"（AA）给出了**具体的替代形态** **[官方规范]**：滑块旁边给一个文本输入框，或**列表项旁给可点击的上下移动控件**。

**WCAG 2.5.2 Pointer Cancellation** 要求优先在**事件结束（up）时**激活；长按弹出的菜单必须可中止 **[官方规范]**。

→ 三条落地：
1. [06](06-日历视图.md) §6.1 的"指针下方跟随半透明块"正好符合 HIG，但**没有写"拖过阈值才出"**——应加 3pt 阈值，否则点选事件会被误判成拖拽。
2. [06](06-日历视图.md) §6.3 的键盘等价路径只有"按 Enter 弹数字输入"，应明确对齐 WCAG 2.5.7 点名的**"上下移动按钮"**形态（对时间轴上移动一个事件，比输入时间戳更常用）。
3. **非法目标无高亮 + 落位失败要撤销而不是弹确认框**——C002 冲突时（[06](06-日历视图.md) §6.1）应当**可撤销**，而不是让用户先确认。

MDC-Android `MaterialCalendarGridView` 有一条可借鉴的细节：**方向键落在禁用日上时自动跳到最近的有效日**，而不是把焦点卡住 **[官方源码]**。本项目的月网格目前没有"禁用日"，但补位格（相邻月份的日子）应当**可聚焦但不可操作**，与真实日区分开。

### 3.6 重叠布局的算法（可引用，且比原方案更简单）

**日视图/周视图的并排列数问题就是区间图着色（interval graph coloring）**：把互相重叠的事件分到最少的列里，答案是图的最大团 = **最大同时重叠数**，而贪心**按左端点排序**就能达到这个最优，**线性时间** **[算法经典，CLRS 第 16 节 / p.379 区间调度]**。

对应到实现（`[06](06-日历视图.md)` §4.3）：

```
1. 取当天全部事件，按 start 升序
2. 为每列记住它最后一个事件的 end
3. 依次为 ev 找**第一个** end <= ev.start 的列，放进去；没有就新开一列
4. 列数 = 最大同时重叠数（已是最优）
```

**这一步就消掉了上一版文档里"事件 A 跨了两个 cluster、在两处都画一遍"的技术债**——因为事件从始至终只属于一列，不存在"跨 cluster"的情况。上一版那个 cluster 划分是多余的中间结构。

剩下的**"同簇等宽展开 vs 左对齐固定宽留白"**是纯呈现选择（Google 日历展开、Outlook 有时留白），不属于算法。本设计选**展开到 100%**：一行内所有事件不重叠时铺满，有重叠时按上一步得到的列数等分。**[呈现选择，非引用]**

### 3.7 颜色语义

**WCAG 1.4.1 Use of Color**：颜色**可以**编码信息，但**绝不能是唯一的编码**；失败准则 F81 明确把"仅用颜色表达必填/错误状态"判为失败 **[官方规范]**。

IBM Carbon 的告警色按**状态**分配（error / warning / success），并**不鼓励用渐变**承载语义 **[官方设计系统]**。

→ 与 [06](06-日历视图.md) §5 的三通道设计同向，但论据要换：不是因为"单信号色好看"，而是因为**单靠颜色区分状态在 WCAG 1.4.1 下不可接受**。三通道（边框样式 = 窗口类型 / 底色 = 状态 / 角标 = 优先级）里，**边框样式与角标是形状与文字，不受 1.4.1 约束**，这是它成立的根本原因。

一个直接结论：**逾期标记不能用红色**。本项目有 `--t-color-danger` / `--t-color-warning`，但日历事件块若用它们编码逾期，就落入 F81 风险区（除非同时有图标）。[06](06-日历视图.md) §3.4 用 `⚠` 图标是对的，继续保持。

### 3.8 排程的失败模式

| 失败模式 | 描述 | 本设计的应对 |
|---|---|---|
| **过载日（overbooking）** | 建议算法把所有任务塞进同一周 | `capacity` 字段显式回报容量占用；空闲集用**工作时段**而非整天（[05](05-排序与推荐.md) §3.2） |
| **算法不被接受（algorithm aversion）** | 见 §3.9，这是本设计最实的风险 | 每条建议带理由（P8）；可整批关图层（[06](06-日历视图.md) §5.3）；永不自动落位（P9） |
| **GTD：日历只放有硬时间点的事** | 会议、预约进日历；任务本身不进 | 本设计的折中：任务的**执行时段**进日历（`planned`），但**不自动进**。GTD 官方教练 Janet Riley 也说给重要任务 blocking "is appropriate and not in conflict with GTD best practices"，但加了一句 **"The most important guide is that you honor that blocked time"** **[官方]** —— 落位之后不执行，是 GTD 视角下真正的问题，所以本设计把"建议"与"承诺"在视觉上分开（[06](06-日历视图.md) §5.3 的虚线） |
| **时间盒自身坍塌（planning fallacy）** | 估的时长系统性地偏乐观 | Kruer & Evans 2004 已确认的规划谬误 **[权威]**。本设计本期不学预估（[05](05-排序与推荐.md) §6 已记为后续项），但 `confidence: low` 的显式标注是这个认知偏误的第一次让步 |

**一条被证伪的说法要记下来**：上一版文档写"'日历填满'反而降低执行力，Cal Newport 明确反对把任务塞进日历"。本次调研**没有找到**任何可靠来源支持"填满日历降低执行力"这个命题；Cal Newport 确实写过 time blocking，但流传最广的"时间盒让效率提升 53%"那个数字，追到源头是 Entrepreneur 博客与 Quantime 营销页，**不是研究**，Wikipedia 自己的条目上还挂着 `[needs more citations]` 标签 **[核查结论]**。Newport 原文"Running your day from a to-do list ... leads to sub-optimal returns" 说的是**从待办清单驱动一整天**这个做法，不是"日历不该有内容"。P9 的依据因此**不来自**"填满日历有害"，而来自**算法 aversion**（§3.9）——那个有实证。

### 3.9 为什么"只建议、不自动落位"是有实证的

这一节是本次调研对本设计最有价值的新增，直接支撑 P8/P9/P10。

**算法 aversion（Dietvorst, Simmons & Massey, 2015）**：让人们预测同一批题，看到算法犯错一次之后，**对算法的信任会比对人的信任掉得更快** **[权威，已读原文 PDF]**。作者自己的解释是：人们能接受人犯错，是因为**人犯错时看起来像是知道自己在做什么**；算法犯错没有这个信号，于是每次都像"模型本身错了"。

对应用的推论很硬：**自动排程只要错一次，用户就可能永久退回手动**——而手动正是 P9 想要保留的。所以自动落位（哪怕用户此刻觉得好用）的**长期期望是负的**，而建议 + 人工采纳的期望是正的。

**Kocielnik, Amershi & Bennett（CHI 2019）"Will You Accept an Imperfect AI?"**：同样是 50% 的准确率，**错误的类型不同**（误报 vs 漏报）会让用户感知的准确率和接受度显著不同；而且**事先校准期望**能提高接受度 **[权威]**。

→ 落地两条：
1. **误报的代价高于漏报**。所以置信度低时**宁可不建议**（[05](05-排序与推荐.md) §3 的 `confidence: low` 走弱化样式而不是隐藏，理由是"漏报会让人以为系统坏了"，但**绝不因为"可能有价值"就强推**）。
2. 建议首次出现时**说清它的能力边界**——"基于你已安排的时段"（[06](06-日历视图.md) §7 末段已经在写这句，**依据现在有了**）。

**Timefold**（OptaPlanner 作者自己的分支，2023）的一句话是本设计的题眼：**"Optimization projects don't fail on math. They fail on adoption."** 它把"能被采纳"拆成四条要求 **[官方]**：

| 要求 | 本设计的对应 |
|---|---|
| **正确且可行**（它说 "80% feasible is 100% useless"） | 建议必须真的落在空闲集内（[05](05-排序与推荐.md) §3.3），排不下就明说排不下（§5 降级表） |
| **可解释** | P8，每条建议带理由（[05](05-排序与推荐.md) §4） |
| **坦白失败**（说明是哪条约束导致了结果） | `unscheduled` 数组显式回报"排不下的理由"，而不是静默丢弃（[05](05-排序与推荐.md) §3.1） |
| **可调整**：planner 能**固定（pin）、覆盖（override）、提案（propose）并即时看到影响** | P10 约束可被用户改；采纳是**一步**，不采纳是**零步**；提供"把这个固定到明天"而不是只给"采纳/拒绝" |

**XAI 侧的两条方法论** **[权威]**：
- Liao, Gruen & Miller（CHI 2020）*Question Bank*：**不要凭空设计一个解释器**，要先枚举用户会问的问题，再决定哪些值得答。对本设计就是：采纳率、拖拽率、图层开关率比"解释文案好不好"更能说明它有没有用。
- Amershi et al.（CHI 2019）18 条 XAI 指南：其中"系统能力范围内的事才解释"、"按用户类别定制"两条正好对应"排序理由按因子类型给出不同粒度"。

**关于用什么算法**：OR-Tools 的 CP-SAT 官方定位是 **"based on feasibility rather than optimization"**，而它文档里的排程示例（护士排班、班次、工厂）**全部是多主体资源调度** **[官方]**。装箱本身是 NP-hard，且在线/离线之别在于未来任务是否已知——个人日程里未来任务**永远不完全已知**，所以本质上只能做在线贪心。**结论：不要引 OR-Tools**，[05](05-排序与推荐.md) §3.3 的贪心是正确量级的选择，理由是问题规模不是算法强弱。

### 3.10 排序模型

| 模型 | 原始出处 | 适用性判断 |
|---|---|---|
| **艾森豪威尔矩阵**（urgent × important） | **出处有争议**：The Quote Investigator 追到 1954 年一篇署名 "former college president"（前大学校长）的无名文章，** Eisenhower 本人没有说过**；且最早版本里没有 "seldom" 一词 **[核查结论]** | 作为**分类框架**（四象限视图）合理，作为自动排序依据太粗。本设计借语义（p1 = urgent+important），不借形式。**引用它时别说"艾森豪威尔说过"** |
| **WSJF**（Weighted Shortest Job First） | SAFe | **前提就不成立**：WSJF 的 Cost of Delay / Job Size 假设**稀缺的多主体产能**（团队里多人抢同一资源），单人日程里"延迟成本"没有可比标尺。**用它排个人任务是把企业工具用错了场景** **[推断，基于前提分析]** |
| **ILP / Voorhees** | 学术文献 | 同上，团队级 |
| **加权乘积 + 稳定次级键** | 通用推荐系统做法 | ✅ **本设计采用**。项目内 `src/modules/mem/selection.rs:53-99` 已是同形状的先例（FSRS 召回紧迫度 × 难度 × 遗忘次数 × 逾期天数） |

**最接近的内部先例**：`mem/selection.rs` 的 `review_candidate_weight`（`:53-72`）。它的因子与本设计的 `due_factor` 惊人地相似：

```rust
// src/modules/mem/selection.rs:62-72（现状）
let until_due_days = days_until_due(&candidate.due_at, now);
let due_factor = if until_due_days > 0.0 {
    // 未到期：越近越加权
    (1.0 + until_due_days).powf(-1.0).max(0.05)
} else {
    // 已逾期：每逾期一天加权
    1.0 + OVERDUE_GAIN_PER_DAY * (-until_due_days).min(30.0)
};
```

**本设计为什么不用同一形状**：记忆到期是**连续的**（今天复习和明天复习，效果差异是渐进的）；任务完成是**离散的**（任务有终点，远期任务今天做和 5 天后做没有本质区别）。所以 `due_factor` 改用分段函数、远期**塌缩到常数**而非持续衰减（[05](05-排序与推荐.md) §2.2）。这是有意的分歧，不是疏漏。

而测试 `weighted_policy_exposes_hard_cards_more_than_due_order`（`selection.rs:221`）表达的直觉——"加权策略确实比纯 due 排序更早暴露难项"——被本设计继承为排序性质之一。

## 5. 一个反复出现的模式

跨厂商看下来，有三件事在**所有**成熟产品里都做了，而它们恰好是本设计的三条主张：

| 所有成熟产品都做 | 本设计的对应 |
|---|---|
| 收件箱是无需成型的唯一去处 | P6 + [03](03-录入模型.md) §4 |
| 行内语法 + 逐词撤销 + 全局关闭 | P4/P5 + [03](03-录入模型.md) §2.3（**但我们不需要逐词撤销，因为我们不解析**） |
| 非名称属性默认隐藏，按键唤出 | P3 + [03](03-录入模型.md) §1 |

而本设计**领先于**它们的地方只有一处：**把"先做哪件"完全交给系统算，并强制每条结果给出理由**。Todoist 有 AI 整理收件箱（无准确率数据），Things 有 Today 视图（靠"是否标记"而非计算），没有一家把"可解释的加权排序"作为一等公民。

**这是本设计的赌注，也是它的风险**（见 [08](08-实现路线.md) 的"风险"章 R1）。
