# 09 · 条件式任务行

> 状态：现行（已实现） · 代码基准：`main@48996cd7`（2026-10-22） · 最后核对：2026-10-22
>
> 实现落点与本文的差异：任务行不再内联展开条件编辑器（只保留状态切换与删除，
> `web/src/domains/task/components/TaskRow.tsx`），条件编辑收在 `/task/:id` 聚焦页
> （`TaskFocusPage.tsx`）与录入框（`CaptureInput.tsx`）；`+` 条件菜单目前只出现在录入框里。
>
> 一句话：**一条任务只有状态和一句文字是必有的；计划时间、截止时间、优先级、时长、标签都是"条件"，需要哪个加哪个。**
>
> 本文件取代 [03](03-录入模型.md) §6 与 [08](08-实现路线.md) 里"行内悬停图标 + 六控件面板"的交互口径；
> 数据模型（[04](04-数据模型.md)）不变，仍然只用已有的 `start_at` / `due_at` / `priority` / `effort_estimate_minutes` / `tags`。

## 1. 为什么改

上一轮把"后添加"做成了行内两个悬停图标（标签、截止），录入框则是一展开就摊出六个控件。它们各自都成立，
合起来却把每一行都画成了表单：

- 一条只想记下来的任务，行尾仍然摆着编辑、删除、加子任务，编辑再打开三 Tab 模态 —— 视觉上"这条任务有很多东西要填"。
- 录入框一展开就是六个控件，用户得先理解六个字段才敢用。
- 加属性没有统一入口：标签一个图标、截止一个图标、优先级只能在录入框里、时长也只能在录入框里。

参考产品给出的共同答案是"**先一句话，属性后补**"：Todoist 的快速添加先用一行文字接下任务，日期/优先级/标签
都在同一行里补；Things 3 的快速录入默认只问标题，细节等打开任务再填；Linear 新建 issue 也是先给标题，
属性放在标题下方的一排可选项里；Notion 的数据库行则是"点 + 加一条属性"的典型。**没有一家把六个字段
作为默认界面摊在用户面前。**

## 2. 决策（已与需求方确认）

| 决策点 | 结论 |
|---|---|
| 「+」的归属 | 一个 `+` 两种添加：上半是条件，底部是「子任务」 |
| 已有值怎么显示 | 有值就常驻显示，没加的条件不占位 |
| 「计划进行时间」 | 落 `start_at`，是**软偏好**；不新增字段 |
| 计划结束 | 不单独存；`start_at` + `effort_estimate_minutes` 推出结束时刻 |
| 编辑入口 | 删掉铅笔与三 Tab 编辑模态；标题行内改，属性行内加 |
| 低频编辑 | 依赖关系、可行/实际时段仍保留一个小入口（抽屉里） |
| 录入框 | 与任务行同构：一句话 + `+` 加条件；符号语法继续保留 |

## 3. 任务行解剖

```
(○)  写周报                                            [计划 10-20 14:00] [P1] [~60m] [#工作]   [+]
      今天到期 · 标为 p1
```

- **状态**：行首原生 `<select>` 画成圆点，键盘/读屏行为不变（沿用现状）。
- **标题**：点击进入行内编辑，回车/失焦保存、Esc 取消、空标题拒绝。**没有铅笔按钮**。
- **条件 chip**：计划时间 → 截止时间 → 优先级 → 预计时长 → 标签。只渲染有值的；每个 chip 都是按钮，
  点击打开对应编辑器。
- **`+`**：行尾悬停/聚焦显形（触摸设备常驻），打开条件菜单。
- **删除**：仍是行尾的垃圾桶，确认后删除（低频、破坏性，留在原处）。
- **理由行**：`smart` 排序的理由继续常驻（P8），不藏进 tooltip。

### 3.1 `+` 菜单

菜单**只列还没加的条件**（标签除外 —— 可以继续加第二个），所以条件越加越多时菜单会自然变短：

```
添加
[计划时间] [截止时间] [优先级] [预计时长] [标签]
[子任务]
```

- 「子任务」是动作而不是条件，放在分隔线下方。
- 选择条件后，菜单收起，对应编辑器在行下方展开，焦点进入第一个输入框。
- 条件全部加过之后，菜单只剩「标签」「子任务」——这正是"足够满足需求"的形态。

### 3.2 条件编辑器

| 条件 | 控件 | 落库 |
|---|---|---|
| 计划时间 | 文本日期 + 日历入口（沿用 MD3 契约） | `start_at` |
| 截止时间 | 同上 | `due_at` |
| 优先级 | P1–P4 四个按钮 + 清除 | `priority` |
| 预计时长 | 数字 + 15/30/60/90/120 预设 + 清除 | `effort_estimate_minutes` |
| 标签 | 复用 `TagInput`（去抖 200ms 补全） | `tags`（整体替换） |
| 子任务 | 单行标题，Enter 创建 | `parent_task_id` |

- 日期/时长/优先级：落定即保存（乐观更新，失败回滚），编辑器不强制"保存"。
- 标签：增删即保存。
- 每个编辑器都有「移除这个条件」；清空值等价于移除。
- 切换条件时只保留一个编辑器，避免一屏多张表单。
- 约束：`start_at <= due_at` 在前端先校验，给出人话提示，不把 400 丢给用户。

### 3.3 键盘与焦点

- `+`、chip、菜单项都是真按钮，Tab 可到；菜单支持 Esc 关闭并把焦点还给 `+`。
- 标题编辑、日期编辑都过 `isImeComposing` 闸门（中文选词的回车不能提交）。
- 编辑器关闭/条件保存后焦点回到触发它的 chip 或 `+`。
- 触摸目标 ≥24px（WCAG 2.5.8）；颜色不是唯一通道（正文文字 + 形状 + 图标）。

## 4. 录入框

```
[ 写周报 !p1 #工作            ] [+]
计划 10-20 14:00 ×   #工作 ×
```

- 第 1 层仍是单行回车即建；符号 `!p1` / `#标签` / `~60m` 继续解析。
- `+` 打开同一套条件菜单（计划/截止/优先级/时长/标签/父任务）。
- 已加条件以 chip 排在输入框下方，点击可再编辑；没有加的条件不占位。
- 日期没有符号，只能从 `+` 加；优先级/标签/时长与标题里的 token 仍是同一份状态（改任一侧另一侧跟着变）。
- 提交载荷、失败还原、焦点留在输入框这些既有契约不变。

## 5. 日历：软计划怎么画

`start_at` 是"我大概从这时开始"，不是安排，所以**不建 `time_window`、不参与拖拽**：

- 只有 `start_at`：在周/日时间轴上画一根细竖线（4px 宽，accent 50%，旁边一个小标题）。
- 同时有 `effort_estimate_minutes`：画成从 `start_at` 到 `start_at + effort` 的浅色虚线块，
  透明度明显低于真实的 `planned` 块和 `feasible` 块。
- 该任务已经有 `planned` 时间窗时**不再画软计划**（否则同一件事有两个形状，用户会以为排重了）。
- 月网格暂不画软计划：月视图回答"这个月排了什么"，软计划属于时间轴这一层。
- 软计划层 `pointer-events: none`，不抢真实事件的点击与拖拽。

## 6. 低频编辑

删除三 Tab 模态后，基础属性全部在行内完成；只有两件事仍属于"罕见但必须有"：

- **依赖关系**（前置任务）
- **可行 / 实际时段**

抽屉底部保留一个「关系与时段…」小入口，打开只含这两块的精简对话框；它不再是"编辑任务"的总入口，
也不再承载标题、状态、时长这些常用字段。删除、改状态仍可在列表完成。

## 7. 数据映射（不新增字段）

| 条件 | 字段 | 空值语义 |
|---|---|---|
| 计划时间 | `task.start_at` | `NULL` = 没有计划起点 |
| 截止时间 | `task.due_at` | `NULL` = 没有承诺 |
| 优先级 | `task.priority` | `NULL` = 没表达过（不是 p3） |
| 预计时长 | `task.effort_estimate_minutes` | `NULL` = 没估过 |
| 标签 | `task_tag_rel` | 空数组 = 无标签 |
| 子任务 | `task.parent_task_id` | `NULL` = 顶层任务 |

计划结束时刻由 `start_at + effort_estimate_minutes` **推导**，不入库 —— 这样改时长时块会跟着变，
也不会多出一份必须和时长对账的数据。

## 8. 明确不做

- 不在标题行做自然语言日期解析（误报不可控，沿用 [03](03-录入模型.md) §2 的结论）。
- 不新增"计划结束"字段，不把 `start_at` 塞进 `time_window`。
- 不做批量编辑（多选设条件），仍记为后续项。
- 不把「条件」叫成「筛选条件」：筛选是另一个东西，界面上用「添加」而不是「条件」做动作词，避免混淆。

## 9. 验收

| # | 标准 |
|---|---|
| C1 | 新建任务只要标题；不展开任何面板也能回车创建 |
| C2 | 一条没有任何条件的任务，行内不出现空占位；只有状态、标题、悬停操作 |
| C3 | `+` 菜单只列未添加的条件；加过的条件从菜单消失 |
| C4 | 点 chip 能改该条件；改完不刷新列表（乐观更新） |
| C5 | 清空日期/时长/优先级 = 移除该条件，chip 消失 |
| C6 | `start_at` 晚于 `due_at` 时前端拦住并说人话，不发请求 |
| C7 | 标题点击可改，回车保存、Esc 取消、空标题拒绝 |
| C8 | 条件菜单、chip、标题编辑全部有可访问名；Esc 能把焦点还回去 |
| C9 | 录入框的符号与条件面板仍是同一份状态（改一处另一处跟着变） |
| C10 | 日历只画软计划，不写库；有 `planned` 窗口时不画软计划 |
| C11 | 删除三 Tab 模态后，依赖/可行/实际时段仍能从抽屉的小入口进入 |
| C12 | `pnpm run check && pnpm run test` 全绿 |

## 10. 参考

- [Todoist · Use task quick add](https://www.todoist.com/help/articles/use-task-quick-add-in-todoist-va4Lhpzz)：一行文字先接住任务，日期/优先级/标签在同一个入口补。
- [Things 3 · Quick Entry](https://culturedcode.com/things/support/articles/1231248/)：录入默认只问标题，细节后补。
- [Linear · New issue creation UI](https://linear.app/changelog/2021-03-10-new-issue-creation-ui)：标题是第一输入，属性作为标题下方的可选项。
- [Notion · Create a database](https://www.notion.so/help/create-a-database)：数据库行的「+ 添加属性」是"按需增加一列"的通用心智。
- [Apple Reminders · Add or change reminders](https://support.apple.com/guide/reminders/remndc729e28/mac)：详情里的日期、优先级、标签都是可加的附属项。

> 前两份与 Linear 的结论与 [07](07-调研附录.md) 一致：**录入成本的决定因素是"默认要填几个字段"，不是字段本身有多少个。**
> 上一轮把六个字段都放在展开面板里，等于默认要求用户先看一眼；这一轮把它们变成"想加才加"。
