## 1. 结论先行

预览的**类型覆盖**已经很全（20 个查看器，见 `file-service.md` §8.4），短板不在"能不能看"，
而在**看的过程中**：

1. **出不去**：失败只有一句文案（无重试）；内容被截断只有一句文案（无载入更多）——
   用户被卡住时没有下一步动作。
2. **读不深**：文本/代码/日志没有查找；epub 不记阅读位置、没有目录 —— 高频的"读"场景缺工具。
3. **看不清/不趁手**：图片灯箱不能缩放；表格首行不当表头、500 行硬截断；音视频是裸播放器。

因此排期按"先补出口、再补阅读工具、最后补查看器能力"推进。**第一轮不动后端**。

## 2. 已确定的产品决定（勿反复）

- **详情页 `/file/:id` 是"单个文件"的页面，不做跨文件导航。**
  曾经的「上一个/下一个」按钮、方向键切文件、以及图片灯箱的跨文件翻页**均已移除**：
  `/file/:id` 是文件汇集里的一条，相邻文件之间没有语义关系（不是相册、不是书），
  给"下一个"只会让人误以为它们相关。浏览一组文件回**列表页** —— 那里灯箱的翻页按当前
  筛选结果来，语义成立。回归测试：`FileDetail.render.test.tsx`（无那两个按钮 + 方向键不切文件）、
  `ImageViewer.test.tsx`（灯箱单张、无翻页按钮）。
- **查看器只接收 `{ item }`**，内容获取自己挑 hook。不要为了跨文件的能力往 props 里加东西
  （原先为此加的 `FileNavContext` 已随跨文件导航一起删除）。
- 官方白名单外的格式一律接收（`other` 档），预览层做尽力而为的降级 —— 不是拒绝的理由。

#### P1-1 文本/代码/日志：查找栏 ✅

- **实现**：没有走原计划的"改造 `children: (text) => JSX` 契约 + `<mark>` 包命中"，
  而是**查已渲染的 DOM 文本节点** —— 一套实现就覆盖纯文本、代码、Markdown、CSV、docx、
  epub（它们的共同点是内容最终落在 DOM 文本节点里），且不必碰任何查看器的渲染逻辑。
- **文件**：`lib/findInText.ts`（纯函数，正则转义 + 命中上限 2000）、
  `viewers/FindOverlay.tsx`（浮层：计数 / 环形上下跳 / Esc 清选区）。
- **高亮用浏览器原生选区**：零 DOM 改写，不与 Markdown 标记、代码高亮 span、表格结构打架；
  代价是同时只突出一个命中，用"3 / 17"的计数补上"一共多少处"。
- **已知限制**：跨节点的命中找不到（查询串跨越标签边界，如 Markdown 里 `**粗**体` 的"粗体"）。
- **注意**：没有引第三方高亮库；`markdown-vendor` 仍是懒加载。

#### P1-2 文本/代码：行号 + 换行开关 + 复制全文 ✅

- **实现**：`viewers/PreBlock.tsx`，用在 PlainTextViewer 与 CodeViewer 的退回分支。
- **行号刻意不用 `<ol><li>`**：一行一个 DOM 节点，十万行的日志就是十万个节点，而大文件
  恰好是这条路径最常见的输入（这正是当初给文本预览设上限的原因）。改成**一个等宽文本
  节点**装编号，DOM 恒定两个文本节点（测试用节点数 + 末尾编号钉住）。
- **行号只在"不换行"时显示**：折行后一行占多行高度、左侧编号必然错位（那时它在说谎）。
  因此 PreBlock 里正文默认 `white-space: pre` ——**这是相对旧行为的变化**（原先 `.pre`
  是 `pre-wrap`，长行会折）。
- 高亮那条路径（≤10 万字符）没有行号：行被 hljs 拆成了 span，逐行编号要另做一套。

#### P1-3 epub：目录 + 阅读位置 + 字号 ✅

- **目录**：书名位置换成章列表下拉（带序号）。原计划说"侧边或弹层"，实际用原生
  `<select>` —— 键盘可达、无需自造弹层、几十上百章也就是一个长下拉。
- **阅读位置**：章号 + **章内滚动比例**存 localStorage。只存比例不存像素（换字号/窗口后
  同一像素落在别处）。恢复要有界重试：正文经 DOMPurify 异步注入，容器先是没有高度的。
- **越界的存档从头读，而不是夹到最后一章**：书被替换过时，夹到末尾会让人以为"读完了"，
  实际是另一本书的尾部。
- **字号**：四档，作用在正文容器的 `font-size`（正文是 em 排版，外层一改就整体缩放）。
- **文件**：`lib/bookProgress.ts`（纯函数）+ `viewers/EpubViewer.tsx`。

### P3 —— 需要后端的（单独排期）

#### P3-1 预览分页：不透明游标（接口形状已定，见下）

**接口**

```
GET /api/file/{id}/preview                  # 首屏：与今天完全一致
GET /api/file/{id}/preview?cursor=<opaque>  # 续取：同一个响应 schema
```

响应**形状不变**（仍是 `DocPreview` 判别联合），只多一个可选字段：

```jsonc
{ "kind": "sheet", "sheets": [...], "truncated": false, "next_cursor": "7b2276..." }
```

**为什么是"不透明游标"而不是 `?row_offset=200`**

1. **客户端不必知道每种类型怎么寻址**。行的单位在 sheet/database 是"行"、在 pptx 是"张"、
   在 epub 是"章"、在 archive 是"条目"、docx 干脆是一整块 HTML —— 每种一套查询参数的话，
   查询串会被污染，且客户端要记住"哪套对哪种"。
2. **加类型不改客户端**。今天只实现 sheet 与 database 两种的行分页，将来给 pptx/book/archive
   加游标时，客户端一行不用改（它只会把拿到的 cursor 原样回传）。
3. **游标是自己发的，服务端可以校验**：`kind` 对不上就当没有 cursor（从头发），
   越界的偏移一律 clamp —— 客户端伪造游标没有任何收益。

游标本体是 **hex(JSON)**（`{"v":1,"kind":"sheet","sheet":0,"row":200}`）：不引 base64 依赖
（仓库已有 `hex`），可读、可测、长度无所谓（它只是 URL 上的一个查询参数）。

**服务端怎么知道"还有更多"**：**多取一行**（`LIMIT n+1`，有第 n+1 行就发游标）。
这也顺手绕开了 `COUNT(*)` —— 大表上那是全表扫描，与 5 秒超时的取舍不值当
（见 §8.10 已认账的那条）。所以数据库表格**报不出总行数**，只说"还有更多"。

**分页的收益要说清**：它省的是**首屏**（响应与渲染都有界，用户自己决定要不要更多），
**不省服务端解析**——xlsx 每次都要整本读进来（calamine 的打开成本无法按行切）。
所以别把它当成"服务端性能优化"。

**落地状态 ✅**：sheet 与 database 的行分页端到端跑通（后端 8801f09f + 前端 f8ab5b94）；
docx / pptx / epub / archive 仍是老样子（截断 + 下载），但接口形状从第一天就是通用的 ——
给它们加游标只需在各自的解析里接上 `Cursor` 并回报 `next_cursor`，**前端一行不用改**。

前端侧的合并规则在 `lib/previewPaging.ts`：**只追加到游标指定的那个容器**，
其余容器沿用已有内容（服务端每次都会把它们原样带回来，用旧的既省事、
也避免把"另一张表的第一页"重复追加）。

#### P3-2 列表缩略图（**已实施**）

原计划只覆盖视频海报帧；实施时扩成"整条列表缩略图链路"，因为图片那条更亏：
列表此前把**原图**下给 240px 宽的卡片（一台相机照片 12MB，一页 24 条能拉几百 MB）。

**后端：`GET /api/file/{stored_id}/thumb?w=320`**（`src/modules/file/thumb/`）

- 惰性生成 + 磁盘缓存 `uploads/file/thumbs/{content_hash}-{宽}.{jpg|png}`，
  命中缓存就是一次小文件读；绝不在上传路径里生成。
- **宽度走固定阶梯 160/320/640/1280**（就近吸附，缺省 320）：不约束 `w`
  会让缓存目录被任意宽度填满（每档一份产物）。
- 缓存键用 `content_hash`（无哈希的存量记录退回 `stored_id`）。
- 两条生成路径，**刻意分开**：位图走 `thumb/image.rs`（同进程 `image` crate +
  `Limits` 限额），视频走 `thumb/video.rs`（ffmpeg **子进程**抽帧）。后者是隔离，
  不是省事 —— 视频解码器的 CVE 历史比位图长得多，别把 libav* 链进主进程。
- 四道闸门：像素数 >60MP 直接回原图（报错会让一张正常照片变成徽章，硬解会把
  cgroup 的 `MemoryMax=1G` 吃穿）、解码限额、并发 2（视频并发 1）、单次 10s（视频 8s）。
- **ffmpeg 缺席即永久降级**：`available()` 进程内只探一次，不可用回 415，
  前端那条 `<img onError>` → 后缀徽章的链路接住（与"类型不支持"同一条路）。
- 目录名 `thumbs` 不是 12 位 `stored_id`，所以一致性扫描与孤儿清理天然忽略它
  （安全，但也不会回收）→ 回收责任在 `service::maintenance::prune_thumb_cache()`
  （200MB / 5000 个上限，按 mtime 删最旧，并清 `tmp_` 残留）；启动自检多一行
  非致命报告（`[5/5] 缩略图缓存`）。

**前端**：`lib/thumbnail.ts` 按后端给的 `thumb_url` 拼 `?w=` 与 srcset（卡片 [320,640]、
列表行与选择器 [160,320]）；**竖图与长图改 `contain`**（宽高比 <0.9 或 >2.0）——
16:10 硬裁会把手机竖拍与长截图的主体切掉，这类图同时亮出 160 档缩略图做的模糊底衬
（几 KB，形状接近 16:10 的图不请求它）。

**视频海报帧的落地形态**（照本文档原来的三条路线评估，走的是路线 A）：

- `ffmpeg -nostdin -v error -ss 1 -i in -frames:v 1 -vf scale={宽}:-2 -threads 1`，
  `-ss` 在 `-i` **之前**（快速 seek），8 秒超时，`kill_on_drop`，并发 1；
  比 1 秒还短的片子自动回退 `-ss 0`。
- 二进制**随部署产物走**：`deploy/ffmpeg.lock` 钉版本与 sha256（没填就拒绝下载），
  `just fetch-ffmpeg` 取到 `vendor/ffmpeg/bin`，`just build` 拷进 `build/bin`，
  `just deploy` 同步并补执行位。
  路径解析顺序：`FFMPEG_PATH` > 应用同目录 `bin/ffmpeg` > PATH。
- **时长**：`duration_ms` 这一列此前从来没人写过（上传路径只解析图片尺寸），
  本文档原来那句"时长已在记录里"是错的。现在两条来源：上传前前端读一次
  `loadedmetadata`（`lib/mediaDuration.ts`），以及出海报帧时用同目录的 ffprobe
  回填（`set_duration_ms_if_null`，只在为空时写、**不动 `updated_at`**）。

**非图片文件的内容缩略**（`web/src/modules/file/lib/thumbPreview.ts`）：文本/代码用
Range 取前 1KB 渲染 6 行等宽小字；office / 电子书 / 压缩包 / 数据库复用 `/preview`
JSON 取前几行。私密与缺失不取；失败即退回后缀徽章。取数有模块级缓存 + 在途去重 +
并发 2，**没有引入 IntersectionObserver**：一页最多 24 条，并发 2 已经够了。

**PDF 首页（已实施，走前端 pdf.js）**：三条路线实测后的取舍 —— ffmpeg 解不了 PDF
（静态构建里没有 PDF 解码器，实测报 `Invalid data found`），poppler/mupdf/pdfium
都没有"随产物走"的静态发行渠道（要 apt/root 或自己编，与本文档对 ffmpeg 的部署
决定相冲），所以代价落到体积上：pdf.js 核 121KB gz + worker 355KB gz，**动态 import
不进首屏**（实测产物：`pdf-*.js` 独立 chunk，首屏 `index` 与 `FileList` chunk 里
pdf.js 内部符号为 0）。渲染第 1 页到 320px 的 canvas → JPEG blob URL，**只在卡片
进入视口后才开始**（这次上了 IntersectionObserver：单次成本比文本片段高两个数量级），
失败退回后缀徽章；blob 与模糊底衬共用同一张图，底衬因此零成本。

**尚未做的**：TIFF/AVIF/HEIC 缩略图（`image` crate 解不了）、音频波形图、
私密文件在列表里的缩略图（`<img>` 不带凭据，仍只显示锁徽章）。

#### P3-3 预览解析结果缓存

- **现状**：靠 `Cache-Control: private, max-age=86400` 让浏览器缓存，换设备/清缓存就重解析。
- **做法**：按 `stored_id + content_hash` 缓存解析结果（磁盘 JSON 或内存 LRU），
  失效随文件删除/替换；与 P3-2 的产物缓存可以共用一套目录约定。

#### P4-3 可访问性 ✅

- **灯箱的焦点管理**（此前完全没有，而 `aria-modal="true"` 已经声明了外面是惰性的）：
  打开把焦点收进对话框、关闭还给触发元素、Tab 在对话框内回绕。
- **踩过的坑**（值得记）：焦点回填写在 `onCleanup` 里不管用 —— 卸载时 Solid 移走这段
  DOM，而被移走的正是当前焦点元素（关闭按钮），浏览器顺手把焦点丢回 body，盖掉了
  刚设的那一次（微任务、宏任务都试过）。正解是**先让父组件卸载、再回填**：放进
  `close()`，三条关闭入口（Esc / 点遮罩 / 关闭按钮）都走它。
- aria-live 那半条由 P4-2 一起落地。

#### P4-4 预览区/侧栏可拖拽调宽 ✅

- **实现**：`lib/splitPane.ts` + 详情页的分隔条。存**像素**不存比例（侧栏里是键值对文本，
  "多宽能读"是绝对量）。拖拽用指针捕获，键盘左右方向键也能调（各 16px，方向与鼠标一致）。
- 分隔条用 `<hr>`：它的隐式角色就是 `separator`（ARIA 的 window splitter 模式），
  既不必声明角色也过得了 biome。
- 宽度经自定义属性 `--side-width` 传下去，**不用内联 width + `!important`** ——
  那会踩 stylelint 的 `declaration-no-important` 门禁。

#### P4-1 查看器操作提示（未做）

`?` 唤起当前查看器的快捷键/操作说明。3DGS 的两套移动模式各有十来条键位，现在只能靠
`MODE_HINT` 一行字与按钮 title —— 值得一块说明面板。

#### P4-5 深链到查看器内部状态 ✅

- **格式**：一个参数 `?view=<查看器id>:<状态串>`（`epub:12` / `xlsx:1` / `database:0` /
  `hex:4096`）。为什么不是 `?chapter=12&sheet=1`：一页只可能有一个查看器，塞一堆各自的
  键名会让 URL 变成杂物柜；id 前缀决定归属，不匹配的查看器直接忽略。
- **只认十进制数字**、**越界当没给**（链接可能来自上一版文件：那时 30 章、现在 12 章）。
- 接线：详情页用既有的 `useUrlParams` 提供 `ViewLinkContext`，四个查看器按需取
  （取不到就退化成只有本地状态 —— 查看器单测不必造假路由）。
- epub 那边 **URL 优先于本地进度**：别人发来的"这一页"就该落在他说的那一页。
- **未覆盖**：pptx / archive 的位置是滚动量、3D 是相机姿态（连续量、序列化价值低），
  有意不做 —— 要加时按同一格式扩一个 id 即可。
- **与 P3-1 的游标是两件事**：游标是服务端分页的位置（对用户不可见），
  深链是用户可见的视图状态。
